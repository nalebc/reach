# Reliability audit — 2026-10-10

Scope: what can make Reach leak memory, stop or stall while you're away from the Mac, or let something through when it should refuse. Agent admission security was audited on Oct 9 (`docs/AUDIT_2026-10-09.md`, removed from `docs/` in `6f5c5c1`; see git history) and is not repeated here.

Method: read the server (`server/`, 48k lines), the launcher (`scripts/launch.mjs`, `scripts/bootstrap.mjs`), the hooks and the phone's live-screen code; sampled the running Reach (pid 44412) once a minute; reproduced the failures marked **reproduced** with scratch scripts in a temporary folder. The audit itself changed no code (the fixes below came after), and the live Reach was never stopped, inspected with the debugger or crashed on purpose. Audited: the working tree on top of `77e3d8f`, including the uncommitted edits of other sessions; line numbers may drift as those land.

Threats considered: ordinary failures (full disk, kills, power loss, network changes, odd agent output) and, as on Oct 9, a malicious or looping admitted agent that triggers them on purpose. A Full control agent can fill the disk and run commands in a loop.

## Fixed (Oct 10, same day)

Every finding below was fixed, plus the request that logs be capped. Tests named per item; all new and touched suites pass (session hosts 496/496, Reach-level suites 585 with 3 platform skips). The server changes take effect at Reach's next start (the Reach started at 12:18 already runs most of them).

## Findings

| # | Severity | Finding | Evidence | Proposed fix |
|---|---|---|---|---|
| H1 | High | **Any crash takes Reach down until someone is at the Mac.** Reach must run in a Terminal window (screen and control permissions), and that window runs Reach once: `start-in-terminal.command` exits when it does. There is no `uncaughtException` / `unhandledRejection` handler, so on Node 24 one unhandled rejection or one `'error'` event with no listener ends the process. Concrete triggers: the `tailscale.log` write stream has no `'error'` listener (`scripts/launch.mjs:230`), so a full disk or an I/O error crashes Reach; the approval monitor runs `mkdirSync` / `readdirSync` / `rmSync` every second with no `try` (`scripts/launch.mjs:412` → `server/device-approval.mjs:47`). Beyond those, 99 fire-and-forget calls (`void f()` with no `.catch`) each rely on the callee catching its own errors. The ones spot-checked do, but one regression anywhere is an outage. The background service has launchd `KeepAlive`; the Terminal mode doesn't. A Full control agent can reach the first trigger on purpose by filling the disk. | Code read. Not reproduced live (it would end your session). | 0. First H3: a relaunch must not undo the owner's pauses. 1. Relaunch in the same Terminal window: the launcher runs the server as a child and starts it again on an unexpected exit, with backoff (1 s, 5 s, 30 s), so the phone sees a short drop instead of a dead Mac. *Needs a check:* that macOS keeps Screen Recording and Accessibility for a child started from the same Terminal. 2. A process-level handler that logs the stack and **exits** so the relaunch takes over. Never swallow and carry on: a half-updated guard is itself a fail-open. 3. Fix the two triggers: an `'error'` listener on the log stream, and a `try` around the approval monitor's body. |
| H2 | High | **The agent command log can stop Reach from starting, and fills up for good.** `createBrowserCommandLog` is awaited with no `catch` (`server/index.mjs:954`). A torn last line, the folder at 0755, or a file over 8 MB / 5,000 lines makes `createReach` throw, so Reach exits at startup (and the background service restarts into the same error every 5 s). A torn line is what a full disk leaves: a partial `write`, then `poisoned` blocks commands for the rest of that run. At runtime there is no rotation: at about 1.9 lines per command, roughly 2,600 agent commands over the install's whole life fill it. After that every agent shell or browser command gets 507 "Command history is full", and nothing in the app clears it. Today: 66 lines, 35 commands since Oct 7. A looping Full control agent could use up the cap in an afternoon and block every agent's commands for good; filling the disk gives the torn line. | **Reproduced** in a temp folder: torn last line → throws 500; folder 0755 → throws 500; at the cap → 507. | 1. At startup, a torn last line is cut back to the last newline and the command is recorded as interrupted. Any other failure starts Reach with agent commands off (503 with the reason), never a failed start. 2. Rotation: when full, the log moves to `commands-<date>.jsonl` (kept, owner-only) and a new one starts. The block stays only for a failed write or an outside change, which is what it protects against. |
| H3 | High | **Pausing one agent doesn't survive a restart.** The owner's per-agent pause ("it can look, not touch") lives only in memory (`pausedAgents`, `server/agent-desktop.mjs:278`). The agent's credential is on disk, so after a crash, `./reach restart` or an update, the agent reconnects **unpaused** and nobody is told. Reach's own Pause is saved (`settings.paused`, `server/index.mjs:801`); this one isn't. Today a restart needs the owner. With H1's relaunch, an agent that can crash Reach (H1's full-disk trigger) could shed its pause by itself. | Code read: the only writes are `pausedAgents.add` / `.delete`; the pause route (`server/browser-agents.mjs:43`) persists nothing. | Save each pause on the agent's record (or `settings`) and restore it at start. After an unexpected exit, Reach comes back with Full control and Apps agents paused until the owner resumes them, and the phone says why. |
| M1 | Medium | **A leftover credential lock disables Revoke.** Credential changes take `clients.json.lock` with `O_EXCL` and remove it in `finally` (`server/core.mjs:283`). A process killed between the two (SIGKILL, a memory kill, power loss) leaves the file. Nothing removes a stale lock at startup, so from then on every change answers 409 "Credentials are being updated": Revoke, pairing, the hourly credential trade, ending a copied credential, the week-unused rule. Expiry still ends access, and Reach's own Pause still works (it's in `settings.json`). The window is a few milliseconds of synchronous writes per change, so it's unlikely, but the owner's off switch stops working when it happens. | **Reproduced:** with a stale lock, `revoke()` → 409 and the device stays listed. | The lock records the holder's pid and start time; a lock whose holder isn't running is removed (and logged). Changes within Reach's own process also take an in-memory lock, so the file lock only arbitrates with the CLI. |
| M2 | Medium | **The Claude transcript cache keeps up to ~390 MB of heap for good.** Budget: 512 MB of transcript *file bytes* kept parsed (`server/agent-sessions/claude.mjs:53`). Measured over this Mac's 21 largest transcripts (409 MB), the parsed form takes 0.76× the file size, so ~390 MB of heap at budget. The bound holds (chats past it keep a summary), so this is a high ceiling, not a leak. This Mac has 703 MB of Claude transcripts; the largest is 121 MB, and an open one is always kept whole. | Measured with a scratch script on the real transcripts; matches the live heap. | Budget by memory, not file size, and lower: e.g. 128 MB, or `os.totalmem() / 64` (256 MB on 16 GB). A chat nobody has looked at for 10 minutes drops to its summary. |
| M3 | Medium | **Codex pictures cached as base64, capped by count, not size.** `sentImages` keeps up to 500 messages' pictures (`server/agent-sessions/codex.mjs:432`), and Codex returns pasted pictures as `data:` URLs (Reach's own `codexImageData` parses them). This Mac's Codex history has 983 of them, ~0.68 MB each. | M4 | Medium | **One odd Codex reply can switch a Codex feature off for every chat until Reach restarts.** In `server/agent-sessions/codex-daemon.mjs`, one unparsable message sets `issues["protocol"]` (line 172), and from then on every Codex call throws (line 294). One reply failing `validateCodexResult` disables that method (line 195): one unusual item in one thread would stop `thread/items/list` for all threads. `issues` clears only when Codex's version changes, not on reconnect. Failing closed is right; failing for everything, forever, is the interruption. | Code read. | The call that got the bad reply fails, with the reason. A reconnect clears `protocol`. Only `-32601` (method removed) stays disabled until the version changes. Log each issue once, so the cause has a name. |

Terminal sockets have no server-side liveness check, so ones the phone abandoned on a network change stay until TCP notices. | Code read. *Needs a check:* whether half-open terminal sockets actually build up through `tailscale serve`. | Log the refusal (route and count, once a minute). Ping terminal sockets as presence does. |
| L2 | Low | **Phone uploads are kept forever.** `agent-images` (content-addressed, 43 MB since Oct 7) and `agent-files` (up to 200 MB per upload) are never pruned; housekeeping only trims logs and old helper builds. This is disk only, and a full disk is what triggers H1 and H2. | `du` of `.reach/quick`. | Housekeeping removes uploads older than 30 days that no waiting message (outbox, drafts) names. *Needs a check:* what else refers to them by path. |

## Checked and sound

- **Host guard** fails closed: an unreadable client list means "active" (`server/browser-host-guard.mjs:93`); a failed identity lookup means 503 and locked.
- **Permission hook** (`scripts/agent-hook.mjs`): any failure prints nothing and Claude Code's own dialog decides. The **mode hook** can only ever say "ask".
- **`clients.json`**: a corrupt or unreadable store gives 503 and is never overwritten (`server/core.mjs:275–296`).
- **The `catch → true` sites** are conservative: paths "overlap", automation "blocked".
- **Long-poll waiters** are removed on timeout and on abort (Claude and Codex).
- **Backpressure** on every live channel: screen (6 frames / 256 KB), screen input, terminal (2 MB, then reconnect), presence (256 KB).
- **Line buffers** from `claude`, the native helpers and Mac prompts are capped (3–12 MB); one-shot reads have timeouts.
- **Funnel lease worker** switches the public route off within 5 s if Reach freezes or dies.
- **Native helpers** that stay running exit on stdin EOF; the one-shot ones read to EOF and exit.
- **Event loop:** the slowest 8 MB parse step of the 121 MB transcript took 54 ms, and the loop yields between steps. The synchronous `ps` in the session registry takes 2–3 ms.
- **Phone:** every object URL is revoked; video frames and bitmaps are closed; intervals and listeners are cleaned up.
- **Child processes:** every `spawn` in `server/` and the Funnel launcher (`scripts/public-link.mjs:170`) gets an `'error'` handler, directly or in its wrapper class. `tailscaleJson` (5 s) and `runTailscale` (20 s) have timeouts.

## Not covered

- The live Reach's heap wasn't snapshotted (that pauses it and briefly doubles its memory); its makeup is inferred from the transcript measurement.
- No live crash, full-disk or network-change test on the running Reach.
- The Swift / Objective-C helpers' own memory wasn't profiled.
- OpenClaw's gateway (1.26 GB now, started with an 8 GB heap cap) is launched by OpenClaw, not Reach.

## Proposed order

1. H3 saved agent pauses, then H1 relaunch + log-and-exit handler and the two concrete triggers (the relaunch never before H3).
2. H2 command log: repair at startup, never fail the start, rotate.
3. M1 stale credential lock.
4. M4 Codex issues scoped to the call.
5. M2 and M3 memory budgets.
6. L1–L4.
