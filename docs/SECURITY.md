# Reach security model and review history

For the current browser-agent preset and tool contract, see [BROWSER_AGENT_TOOLS.md](BROWSER_AGENT_TOOLS.md). Sections dated below record earlier reviews and may describe superseded UI. To report a vulnerability, follow [the security policy](../SECURITY.md).

## Current release model (2026-10-06)

Reach's API and WebSockets live on private Tailscale Serve (port 8443). The shared listener is a user-owned mode-0600 Unix socket in a mode-0700 directory. It classifies **each request**, including reused connections, using the Funnel marker inserted by tailscaled. Identity comes from Tailscale WhoIs, not browser-supplied identity headers. The pinned [Tailscale implementation](https://github.com/tailscale/tailscale/blob/v1.104.0/ipn/ipnlocal/serve.go) strips incoming identity/Funnel headers and sets its own. Never proxy public traffic directly into an unmarked trusted listener.

**Public access is answered on demand.** Port 443 is on Tailscale Funnel while Reach runs, and Reach answers internet requests only while an invitation is waiting to be opened, a browser agent's session is live, or a browser agent has Always access (below), that is, while the window (`funnelWindow` in `server/core.mjs`) is open. A **pairing window** opens it too, so a phone without the Tailscale app can sign in to Tailscale in its browser: for 15 minutes from a `./reach` started in a terminal someone is looking at (not the background service, not a non-interactive start, not a window Reach opened itself for a restart or at sign-in), during setup's phone step, and after `./reach pair`. It is a file in Reach's private folder (`pairing-window.json`, held to 15 minutes whatever it says), and the first new device that gets in closes it (another browser of a phone already approved does not). It opens exactly what an invitation window opens: the start page, Face ID sign-in and the signed agent gateway; the phone still has to be approved at the computer. Outside it every internet request gets 404 "Not found" before any handler runs (`listenPrivate` in `server/index.mjs`). Until 2026-10-08 the route itself was switched on and off with the window, but Tailscale withdraws the public name after Funnel has been off for a while and can take many minutes to publish it again, so a freshly opened route gave agents a link the internet could not resolve. `scripts/ephemeral-funnel.mjs` holds the background route; it is Tailscale daemon state, so it does not depend on a command-line session staying up. Stopping Reach switches it off, a separate janitor process (`scripts/funnel-lease-worker.mjs`) holds a five-second lease on it and switches it off if Reach itself dies, and Reach switches off only a route it recorded as its own. In practice: a guest without the Tailscale app, Face ID sign-in for a new browser, and the command-line agent's join command (which fetches `agent.mjs` from the start page) work only while a window is open; owners with the Tailscale app on their phone are unaffected, since they use port 8443 inside the tailnet.

**What the internet gets while the window is open:** the start-page handler (`server/public-start.mjs`: GET/HEAD of fixed files, 404 for anything else, WebSocket upgrades dropped), two bounded Face ID endpoints (`POST /faceid/options`, `POST /faceid/join`), and the signed agent gateway (`POST /agent-gateway`, `server/funnel-agent.mjs`). The gateway is how an invited browser agent reaches its API: each request is an envelope signed with the agent's P-256 key (ECDSA, a nonce, a one-minute clock window, replayed nonces refused), the gateway's own fixed path allowlist is independent of the application's route table so adding an owner API cannot publish it, and the invitation's per-preset route allowlist (`server/agent-presets.mjs`) applies behind it. TLS terminates on the Mac. Owner APIs and WebSockets are never answered to Funnel-marked requests.

**Browser agents are invited with one preset** (Full control, Apps, Files, Read only) and no per-action approvals; see [Agent presets (2026-10-06)](#agent-presets-2026-10-06) and [BROWSER_AGENT_TOOLS.md](BROWSER_AGENT_TOOLS.md). Full control grants an unsandboxed shell as the owner: commands can read sensitive files and modify Reach, even when a direct API path or visible UI target is blocked. Only grant it to agents trusted with that OS account. The command deny list and protected-window filters are guardrails, not confinement. Selecting a terminal or IDE under Apps carries the same command-execution trust; Files uses its separate sandboxed file boundary and has no shell.

A public passkey assertion must pass challenge, origin, RP ID, signature, user-presence, user-verification, user-handle and counter checks. Registrations require a discoverable credential. Credential IDs, backup flags and duplicate CBOR fields are checked as well, following [WebAuthn](https://www.w3.org/TR/webauthn-3/). A verified assertion mints a one-use tagged Tailscale enrollment key and a separate expiring admission ticket. Only the matching tagged device presenting that secret receives an owner credential, bound to its Tailscale node. A URL, hostname or pairing code alone does not provide this access.

Removing a passkey invalidates pending tickets, stops admission still waiting on Tailscale, and revokes Reach credentials and live connections admitted by that key. Legacy Face ID credentials without key provenance are also revoked conservatively. Devices locally approved through the owner's Tailscale account are separate; revoke those in Access when needed. Tailnet device deletion is asynchronous and retried; Reach access is revoked immediately even if the Tailscale API is unavailable.

Invite-key setup now refuses wildcard-source policies and other detected rules that could give tagged guests more access than the selected Reach port. It does not silently narrow existing rules. The manual OAuth-client setup still requires an administrator to verify effective ACLs. Later policy edits can broaden access: adding a restrictive grant does not override another allow rule. Reach's stored OAuth client has no policy-read/write scope, so it cannot continuously prove network isolation. Re-review policy after changes, including source aliases, subnet rules and additional grants for the guest tag.

Public sign-in has bounded bodies, body deadlines, expiring one-use challenges, per-address rate limits and a global successful-enrollment cap. These limit resource use but do not make public onboarding immune to denial of service. The passkey verifier is custom code; automated vectors and regression tests are not an independent penetration test. Test a real phone and conduct an independent security review before a broad release.

The sections below record earlier audits and individual features. Where a dated section's claim has since changed, a dated note says so. Older private-only claims describe the earlier design.


This is a source review and targeted regression test pass, not a penetration-test certification or a guarantee that no vulnerabilities remain. Scope: Node companion, pairing, scopes, file endpoints, PTY/WebSocket transport, Codex approval routing, launcher/distribution, browser request handling, and npm dependencies. Native iOS packaging received a limited source inspection; Windows and physical phones were not exercised.

### Answering agents' approvals from the phone (2026-10-08)

Reach no longer reads or presses buttons in the Claude app or the Codex app, or types into a terminal, to answer an agent. Those clicks were unreliable, and a press that might have landed couldn't be retried safely.

- **Claude Code (Claude app and terminals):** Claude Code runs Reach's `PermissionRequest` hook (`scripts/agent-hook.mjs`) while it shows its own dialog. The hook reaches Reach only over a mode-0600 Unix socket in Reach's data folder. Reach holds the request for the phone and returns the owner's answer as Claude Code's hook decision. Only the owner's devices can answer (the `sessions` API family is never granted to guests or agents). The Mac's dialog stays up and works: verified with Claude Code 2.1.293, whichever answer comes first applies, and a later hook answer is ignored. Requests from headless runs, subagents and Reach's own sessions get no answer from the hook, so Claude Code decides as usual. The hook is added to `~/.claude/settings.json` only on the owner's tap (`POST /api/agents/claude/phone-answers`, owner only). Other hooks are kept, and a copy of the file goes to `settings-backups` in Reach's data folder. Turning it off removes only Reach's entry. "Always allow" applies only the rule Claude Code itself suggested. A permission mode picked on the phone is sent as Claude Code's `setMode` with the next request the phone allows. Bypass is never sent.
- **Codex app:** Reach answers the chat's own pending request by its id, over the Codex app's user-owned IPC socket (`~/.codex/ipc`). It sends only the decisions that request offers. It reports the request as answered only once the request has left the chat's state; otherwise the answer is uncertain and can't be sent again automatically. If Reach can't tell which request a card is (no matching id and more than one pending), it leaves that request for the Codex app.

## Remaining boundaries and limitations

1. **Reach controls the host OS account.** `exec`, `terminal`, screen control, and Codex are powerful capabilities. An agent with shell access can read local credential files or change the companion itself. API scopes/ownership do not sandbox that agent. Use a dedicated OS account, VM, or isolated computer for untrusted agents.
2. **File access is broad and includes writes.** Without `--folder`, the root is the home directory. A file credential can read sensitive files there and upload new files; hiding dotfiles in the interface is not a permission boundary. Use explicit shared folders. This pass does not claim to prevent symlink races caused by a concurrently malicious local process ; the new profile-based file API enforces per-agent roots as described below.
3. **Browser credentials remain in local storage.** An XSS vulnerability, malicious browser extension, or compromised trusted interface could steal them. Exact origins, CSP, expiry, and revocation reduce exposure; hardware-backed browser keys or an HttpOnly same-origin session design remain future work. No authenticated browser UI or physical-phone penetration test was performed.
4. **Tailnet access policy remains the owner's responsibility.** Serve limits network reachability; application pairing is an additional check. One-command setup requires an installed, signed-in Tailscale client and may require owner approval to enable HTTPS. Local processes can reach the loopback listener. The launcher does not automatically change tailnet grants or install a VPN.
5. **Revocation stops future API and socket access, not all existing effects.** Commands already started may continue; cancellation cannot undo filesystem changes or reliably contain deliberately detached subprocesses. Stop the relevant job/session or companion as appropriate.
6. **Not hardened for hostile public traffic.** There are limits on payloads, jobs, terminals, and pairing attempts, but uploads can consume disk space and authenticated workloads can consume host resources. Keep Reach private. Shared proxy-side rate limits can temporarily block other clients after repeated bad attempts.
7. **Distribution/runtime trust remains.** Node downloads are SHA-256 pinned and npm uses the lockfile; package lifecycle scripts still execute locally. Signed application releases, a sandboxed companion, and independent review remain outside this pass. Windows behavior and user-profile ACLs need device validation.
8. **Running processes must be restarted to receive fixes.** Editing source does not patch an already-running companion. Restarting ends its active jobs/terminals. The audit does not silently interrupt existing user sessions.

No Supabase administrative credential is needed for the default authentication flow. Each host holds its own pairing and client state; Tailscale handles private connectivity, and Reach verifies local client credentials.

## Screen feature follow-up

Screen viewing is off until the owner's first phone is approved, which turns it on (Oct 10: the owner wants their own phone to have the whole computer); an owner's own choice in Settings is kept, and no guest, agent or later device turns it on. Input now requires a separate 30-second, memory-only control grant bound to one paired full-access client; a screen-scoped agent cannot acquire it. The browser renews while actively controlling and releases on pause, page hide, or unmount. Revocation and disabling viewing clear the grant. Native dispatch rechecks authorization after any helper compilation, and simultaneous input operations are rejected. Screenshot responses recheck viewing/auth after capture.

Validation includes control ownership, expiry, revocation, disabled-view behavior, payload bounds, and dispatch through an inert helper. The UI was exercised at phone width with a synthetic desktop fixture; the Swift helper typechecks. This does not establish real desktop capture/control or physical-device behavior. macOS permissions still require the user to grant access locally.

Continuous screen streams authenticate in the first WebSocket message and require the `screen` scope and enabled viewing. Exact Host/Origin and Funnel checks apply before upgrade. A shared native capture process runs only while viewers are connected, rechecks authorization before delivering frames, and stops on the last disconnect. Protocol-2 streaming limits viewers to four, frame bodies to 8 MiB, and each viewer to six unacknowledged packets; outgoing socket buffering is also bounded. Legacy streaming retains a separate four-viewer cap and one-frame window. Slow video viewers resume at a keyframe. Native helpers communicate only over local pipes; no additional network listeners or public signaling servers are introduced. Disablement closes all screen sockets; revocation closes the affected client’s sockets. Streaming does not grant remote input permission.

## Agent CLI follow-up

Named profiles bind short-lived agent credentials to API scopes and canonical folder roots. The server intersects the issued snapshot with the current local policy, so reductions apply to subsequent requests and expansions require a new grant. Missing/invalid profiles fail closed; configured policies reject legacy unprofiled keys. File mutations require `files:write`; file reads require `files:read`. Text edits require the last-read SHA-256 and atomically replace the file. These checks do not protect against a concurrently malicious local process swapping filesystem objects, and shell-capable scopes remain outside folder confinement. Existing command side effects are not undone by revocation.

The agent CLI stores credentials in exclusive mode-0600 files, refuses insecure secret inputs, validates TLS even through the loopback CONNECT proxy, and rejects redirects. The optional isolated Tailscale wrapper uses its own socket, ephemeral memory state, exact-tag verification, disabled incoming/SSH/routes, bounded lifetime and cleanup. It cannot establish that existing tailnet grants are narrow: owners must review additive ACL/grant rules. Same-user processes in the agent runtime are not isolated from its socket, proxy or mounted secrets. Workload identity trust, AWS IAM, tailnet changes and real cloud enrollment require environment-specific validation. See [Agent CLI](AGENT_CLI.md).

### Temporary guests

Connection settings lets an owner create a one-use guest invitation lasting 5 minutes to 24 hours (the API permits 1 minute to 24 hours). The fixed expiry starts at creation, includes time waiting for redemption, persists across restarts, and cannot be extended by the guest. A new invitation is required after expiry. Unused invitations can be revoked from the same client list.

Guests receive only selected shared folders with read or read/write access, and optionally view-only screen access. They cannot use terminals, execute commands, control the screen, manage clients, or issue new invitations. A 256-bit invitation secret is kept in the URL fragment, removed from browser history on opening, stored only as a hash on the laptop, and exchanged once for a different hashed credential under the credential-file lock. Guest browser credentials use session storage, separate from permanent owner pairing. Leaving revokes the guest credential.

Expiry is enforced by the laptop on every request, with deadline timers for active HTTP transfers and WebSockets. Early revocation closes WebSockets immediately and in-flight HTTP transfers within the one-second authorization check. Upload authorization is checked again before a completed upload is published. Downloads already received and completed file changes cannot be recalled. A guest may copy their credential before expiry; it still has the same scope and deadline, so the invitation is not an identity-verification mechanism.

These deadlines revoke Reach access. They do not remove a person or device from Tailscale or revoke access to other laptop services. Guests still need an independently authorized Tailscale path to this laptop. Configure the tailnet to allow only Reach's port when that is the intended boundary; Reach never applies tailnet-wide policy or logs the owner's laptop out of Tailscale.

### Encoded desktop and persistent input

H.264 video and input use separate authenticated WebSockets on the existing Reach listener. They do not open media ports or use external signaling services. TLS through Tailscale Serve and the private tailnet remain the deployment boundary; encoded video does not itself encrypt traffic.

The new persistent input channel requires the owner's explicit control grant and rechecks authorization before and after each native operation. Display IDs, coordinates, keys, modifiers, text lengths, message order, and rates are validated. A connection uses one native helper, serial native dispatch, a bounded eight-action pipeline, and bounded buffers. Authorization is rechecked immediately before queued actions are dispatched. Pointer moves are coalesced client-side. Native watchdogs release held mouse buttons after two seconds without traffic; normal disconnect closes the helper. These are best-effort cleanup under OS/process failure, not a guarantee against a forcibly killed or compromised host.

Clipboard transfer is text-only, explicit, and limited to 16 KiB. It uses the same owner-only control channel, is never automatically synchronized, and is not persisted by Reach. The preview remains in page memory until cleared or the screen view is unmounted. Guests and scoped agents cannot use input or clipboard even when permitted to watch displays. Screen permission covers the available displays; it is not a per-monitor privacy boundary.

Validation covers malformed input, guest isolation, expiry, revocation, drag ordering, shortcuts, clipboard authorization, bounded video delivery, keyframe recovery, and native Mac H.264 output from synthetic frames. Browser verification uses real encoded synthetic video and mocked input, avoiding capture or control of the user's desktop. Windows native helpers and physical iOS/Android gestures still need device testing. No claim of a gap-free security audit or benchmark parity with commercial remote-desktop products is made.

### Automatic desktop and app shortcuts

Performance changes preserve authorization checks at native dispatch and before sensitive responses. Pending input is cleared on close/revocation; native input remains serial even though network transmission is pipelined. Stale queued commands fail closed. Automatic video pacing and bitrate changes do not reconnect or widen permissions. App shortcuts require owner + apps scope and dispatch server-discovered installed app IDs, the fixed new-Codex-session action, or saved validated HTTP(S) website shortcuts. No user-supplied shell command, arbitrary URL scheme, or app argument is accepted. The shortcut's empty composer requires the user's next action before an agent starts work.

### Focused screen typing

Automatic field detection runs only after an owner-controlled click. It reads accessibility role, enabled/editable state, bounds, and password status, never the existing text or label. The helper returns an opaque in-memory focus token. Live edits and field keys verify that token and the current focused element immediately before dispatch. Focus can still change concurrently with OS input; this is a best-effort wrong-target guard, not transactional isolation. The browser keeps only the draft typed in this session, masks password drafts, and discards it when the bar closes or control ends. Existing owner-only control, expiry, payload bounds, and revocation checks apply unchanged. Native Windows behavior and physical-phone keyboards need device validation.

### Native phone editing and selection copy

The phone uses native text controls for selection, cut/copy/paste, autocorrect and dictation; their buffer is only text entered in the current typing session. Explicit manual keyboard entry can use legacy cursor-based input without a focus token when field detection is unavailable. Detected fields retain their focus guard. Copy selected text is an explicit owner-controlled action that reads only the current accessible selection, rejects password fields and limits UTF-8 output to 16 KiB. It does not invoke Copy and then race an old clipboard value. Existing control grants and post-dispatch authorization checks apply. Browser clipboard writes begin in the initiating tap; denied writes fall back to a selectable preview. No automatic clipboard synchronization or text logging was added.

### Saved custom shortcuts

Owner-only shortcut definitions persist as mode-0600 JSON inside the private data directory. App targets must resolve to the installed-app catalog, including at dispatch. Website targets accept only HTTP(S), reject credentials/control characters and are passed as a separate argument to the OS opener without a shell. They are explicit owner-requested navigation, not a server fetch or new network listener. No commands, arbitrary deep links or app arguments can be saved. CRUD and execution require both admin and apps scopes with authorization rechecks after asynchronous discovery. Validation covers persistence, edits, deletion, missing apps, input bounds and guest/agent rejection.

### Tailscale identity and local device approval

The configured Mac/Linux launcher uses a dedicated Unix HTTP/WebSocket listener, mode 0600 under a mode-0700 directory owned by the Reach OS user. On sandboxed macOS Tailscale variants this lives in the existing Tailscale app-group container; on CLI-only hosts it uses a private temporary directory. No Tailscale credentials/configuration files are modified. Only this listener can mark requests as trusted ingress. TCP localhost headers never establish identity. The OS user and root remain trusted: they already have access to Reach's credential files and the computer itself.

Serve overwrites forwarded source and identity headers. Reach resolves that source IP with `tailscale whois --json`; owner access requires the locally pinned numeric user ID and an untagged, non-expired node. Shared external users and tagged agents cannot become owners by presenting a pairing code. New browsers submit a bounded, five-minute request with a random claimant secret. A local terminal decision is required; there is no remote owner-approval endpoint. Claims require the same user/node and claimant secret. A 30-day Reach credential is bound to that identity on every HTTP and WebSocket authorization check, including screen-input checks. Missing Tailscale identity fails closed. Old unbound owner credentials require a fresh approval/pairing; scoped guests and agents retain their original permission model and require the trusted private ingress.

Pending requests and completed approval receipts survive a companion restart. A crash during credential issuance fails closed and asks for a fresh approval, rather than minting a duplicate credential. Retried claims return the same token rather than create another client; revocation cannot be undone by reclaiming the approval. The token is temporarily retained in a mode-0600 approval receipt for response retries, until the five-minute request expires; periodic cleanup runs every 30 seconds while Reach is running, and on subsequent requests. The main client store retains only the token hash. Browser sessions use local storage; pending request secrets use session storage. A copied token is unusable from another Tailscale node, but processes/browser scripts with access to the approved browser on the same node remain inside the trust boundary.

WhoIs lookups are coalesced and cached for two seconds, rather than run per input event/video frame. Active transfers/sockets refresh identity every two seconds, fail closed on lookup failure, and also expire stale identity locally. Reach credential revocation and screen leases retain their existing immediate/one-second enforcement. Tailnet removal is subject to Tailscale's own propagation and Reach's refresh interval, not an instantaneous global guarantee. Approval does not change tailnet ACLs, grant VPN membership, or enable Funnel.

Coverage: setup confirmation and malformed settings, unsupported Serve, TCP header spoofing, missing/invalid forwarded IP, wrong user/node, tagged owners, Funnel markers, pairing fallback gates, claimant-secret checks, expiry/denial/retry, copied credentials, scoped agents, authenticated WebSocket reconnect and revocation. Physical iPhone/iPad and Android onboarding remain hardware acceptance tasks.

Validation for this change: 136 tests passed, TypeScript/Vite production build passed, and the updated QR scanner passed Swift syntax parsing. A disposable Reach instance completed real Tailscale Serve identity lookup, a local approval, authenticated device access, and a retried claim on this Mac; its private route and temporary state were removed afterward. The browser preview verified pending-request reload, approval-to-workspace transition, and disconnected-phone guidance. This does not establish physical phone, Windows, or rebuilt native iOS app acceptance.

### Public start page and browser sign-in (2026-10-04)

This changes the earlier "no public tunnel" position, at the owner's request: phones without the Tailscale app must be able to reach a sign-in page. What is public, and what is not:

**Note (2026-10-06, updated 2026-10-08):** the Funnel route is on while Reach runs but answered only while an invitation is waiting to be opened or a browser agent's session is live, and then it also answers the signed agent gateway (`POST /agent-gateway`, `server/funnel-agent.mjs`), which carries an invited browser agent's API requests under that invitation's allowlist. Read "no API" below as "no owner API"; see [Current release model](#current-release-model-2026-10-06).

- **Public (Tailscale Funnel, port 443):** the start-page handler (`server/public-start.mjs`); since 2026-10-05 reached through Reach's own listener rather than a separate one (see One address below). It answers only GET/HEAD for an allowlist: the start page (`/`, `/guest`), `/reach-start.json` (the private address, computer name and current Reach instance ID), hashed build assets under `/assets/`, the browser Tailscale client under `/tailnet/`, and the favicon, fonts and manifest. Anything else returns 404; WebSocket upgrades are dropped; other hosts get 421; misses are not cached, so arbitrary paths can't grow memory. Its CSP adds only `'wasm-unsafe-eval'` for the client. The app's code is public; it contains no secrets.
- **Private (unchanged):** Reach's API and WebSockets stay on private Serve (default 8443). Funnel on that port is still refused, and Funnel-marked requests are still rejected. Verified from outside the tailnet (public DNS): start files return 200, `/api/health` returns 404, and the private port refuses the connection.
- **App first (before one address):** the start page fetches `/api/health` on the private address. Only the start origin is added to the CORS allowlist for this check. If the answer comes from the same Reach instance, the phone already reaches the computer directly through the Tailscale app, and the page redirects there (keeping `#pair` / `#invite` fragments). Other origins still get 403.
- **Browser sign-in:** without the app, the page runs a Tailscale node compiled to WebAssembly (`tailnet/main.go`, based on Tailscale's `cmd/tsconnect`, pinned to `tailscale.com` v1.104.0). The user signs in on Tailscale's own login page. The node is a normal, lasting device on the tailnet, so tailnet policy, key expiry and device approval apply to it. Its key lives in the page's local storage for the start origin. Reach's API traffic travels inside WireGuard through Tailscale's relays (browsers can't send UDP, so there's no direct path), and TLS to the private address is verified inside the node. The computer identifies it with `tailscale whois` exactly like an app device, and owner access still requires approval on the computer. No logs are uploaded to Tailscale's log service.
- **Limits:** anyone who can script the browser profile can use its node key until it is removed from the tailnet. Safari may clear storage for sites that aren't used for seven days, which means signing in and approving again. Large downloads in this mode are assembled in memory rather than by the browser's download manager.

Coverage: public listener allowlist, methods, hosts, traversal attempts, upgrade refusal, Funnel-marked requests, manifest validation, stale-socket handling; Funnel route ownership (ours, free, taken), foreground restart with backoff, never replacing another service on 443, service-mode add and uninstall removal; browser transport (routing to the tailnet only, streaming Response bodies, abort, empty bodies, WebSocket events, close codes, send order, errors kept out of the Go runtime); start-page config validation, instance-checked probe, redirect targets and wrong-account detection. Live checks on this Mac: the browser path loaded the real app through a browser tailnet node, Reach identified the owner account (`/api/auth/method` eligible), and API round trips measured 17.6 ms median and 24 ms p90 through the Seattle relay. Physical iPhone acceptance is still pending.

### One address (2026-10-05)

At the owner's request, one link works with the Tailscale app on or off: `https://<computer>.<tailnet>.ts.net` (port 443). What changed is where the internet's requests land:

**Note (2026-10-06, updated 2026-10-08):** port 443 is answered on demand (see [Current release model](#current-release-model-2026-10-06)). With no invitation or agent session window open, the one address answers every internet request with 404, and phones use the private address (port 8443) with the Tailscale app. Marked requests now go to the start page, the Face ID endpoints and the signed agent gateway.

- **One listener, sorted per request.** The Funnel route on 443 now points at Reach's own private listener (the owner-only Unix socket that private Serve on 8443 also uses), no longer a separate start-page listener. Tailscale marks each request that came through Funnel with `Tailscale-Funnel-Request` and deletes that header from everything else, including a copy sent by the client (`ipn/ipnlocal/serve.go`, `addTailscaleIdentityHeaders`). The listener decides per request, never per connection, because Tailscale can carry both kinds over one kept-alive connection. Marked requests go only to the start-page handler (the same allowlist: GET/HEAD of fixed files, no API, no WebSockets); they are never marked trusted or looked up with `tailscale whois`, and marked WebSocket upgrades are dropped. Unmarked requests (your tailnet devices) get Reach, exactly as on 8443.
- **Second layer, unchanged:** Reach still refuses every Funnel-marked request (403) and WebSocket, and identity resolution still returns nothing for one. A mistake in the sorting would reach a Reach that gives the internet only refusals.
- **The trade-off:** before, the internet reached a listener with no Reach code behind it; now it reaches Reach's listener and is turned away by a header check on its first line. That check relies on Tailscale setting the mark (tailscaled 1.102.5 on this Mac).
- **Private port:** 8443 stays private Serve (older saved links, linked computers, invitations and guest grants use it). Funnel on it is still refused.
- **Two ways in, one address:** with the app on, the phone is a tailnet device and gets Reach directly. Without it, the start page signs the browser in to Tailscale, and the browser's own node carries Reach's API and WebSockets to the same address (the page's files still load directly). These are two Tailscale devices, each approved on its own (credentials are bound to the device), so the page keeps a saved list for each way (`reach.devices`, `reach.browser.devices`). Whatever this address had saved before (only ever the browser way) moves to the browser list once.

Coverage: per-request sorting on one reused connection (marked, unmarked, marked), 404 for the internet when no start page is set, internet WebSockets refused; the start page's `home` field (same computer, no path, else ignored); the browser routing Reach's paths at its own address through its node; the app-is-on banner asking the phone's own connection (it used to ask the page's node, which always answers); each way keeping its own approval, and the one-time move; the Funnel route replacing only Reach's own recorded older route.

### Face ID sign-in (2026-10-05)

At the owner's request, a new browser of theirs can sign in with Face ID alone: no Tailscale app and no Tailscale login. This is the one place where the owner rule (your Tailscale account plus device approval) has a second form.

**Note (2026-10-06):** the two public endpoints below exist only while the start page is up (an invitation waiting to be opened, or a live browser agent session). At other times a new browser without the Tailscale app cannot sign in with Face ID; a browser on a phone with the app uses the private request-approval path instead.

- **How:** the start page asks for a challenge (`POST /faceid/options`), and the phone answers with a passkey this computer knows (`POST /faceid/join`). This computer then makes a one-time Tailscale key and a one-time ticket. The key is `tag:reach-guest`, single use, preauthorized and expires in 10 minutes; its device is named `rf-<this computer>-<id>`. The ticket is 32 random bytes, kept hashed in memory for 10 minutes. The browser's own Tailscale node joins with the key and shows the ticket from that device (`POST /api/auth/face-join`), which gets it a device credential bound to that node and marked `faceJoin`. Only that route marks a credential this way.
- **What changed in the owner rule:** credentials still bind to their Tailscale node. A tagged node counts as yours only with a `faceJoin` device credential bound to it (`server/core.mjs`). Every other owner check stays on your Tailscale account: Face ID browsers can't add or remove passkeys, linked computers don't vouch for them, and they can't request approval.
- **What the internet can reach:**
  - Two exact POST paths with JSON bodies under 8 KB, limited to 20 requests per minute per address.
  - Challenges have their own pool (32 at a time, 2 minutes, single use), so flooding it can't block Face ID approvals on the tailnet.
  - At most 12 new browsers an hour.
  - An answer must be a verified Face ID (user verification required) from a passkey this computer knows, made on this name's start page or private link, with the user handle present and matching. Passkey IDs are never handed out.
- **The trade-off:** Face ID becomes the only check for a new browser. Anyone who can use a passkey from the owner's iCloud Keychain (their Apple devices, unlocked with Face ID or the passcode) gets owner access, as the owner's Tailscale login did before. A bug in the passkey verifier is now reachable from the internet. Signatures are checked by Node's crypto, and both entry points are tested against real-device vectors and a software authenticator.
- **Network:** the device can reach only Reach's private port on your computers (the invite grant), unless your policy has an allow-all rule.
- **Cleanup:** when a Face ID browser's credential is removed or expires, its device leaves the tailnet. Reach checks on start, every 5 minutes and on removal, with a 15-minute grace while a browser is signing in. A browser whose access ended goes back to Face ID, never to a Tailscale login.

Coverage:
- **Challenges:** the separate pool holds up under a flood.
- **Refused answers:** other origins, registrations, other challenges, presence without verification, unknown passkeys, broken signatures, missing or foreign user handles, and expired challenges.
- **Tickets:** single use, expiry, device name, tagged devices only, and the hourly cap.
- **Keys:** their limits, and cleanup that takes only ended `rf-` devices.
- **End to end, through the real listener:** a Funnel-marked join, then the ticket from the tagged device, then the owner API from that device only. Forged credentials on tagged devices are refused, and removal takes the device off the tailnet.
- **In the browser:** the start page's one-button flow with WebAuthn called in the tap, and Connect using the ticket once.

### Face ID for agent approvals (2026-10-10)

At the owner's request, Face ID on their phone can confirm each agent connection they allow: a switch in Settings → Agents (`faceIdForAgents` in `settings.json`), for the owner's own devices on the owner's Tailscale account only (kind `device` with the `admin` scope and an untagged owner identity, as for managing Face ID itself; a guest's, an agent's or a Face ID-joined browser's credential is refused on the setting and on the challenges, so none of them sees or changes it). It can be turned on only while a passkey is set up on the computer.

- **How:** the review asks `POST /api/agents/admissions/:requestId/passkey/options` for a challenge bound to that request and to the approving device's own credential (`admission:<request>:<credential>` in `server/passkeys.mjs`'s pool: two minutes, used once, ten attempts), and sends the assertion as `credential` with `{decision: "approve"}`. The assertion is checked before anything is decided (the same checks as Face ID for new browsers: origin, RP ID, user verification, signature, counter); while the switch is on, an approve without one gets 403 and the connection keeps waiting. Deny never needs it. An answer made for another request, from another device of the owner's, for a new browser's request, or for the switch itself doesn't verify: every challenge is keyed to its one purpose.
- **A tap can't lift it:** the switch guards against a phone in the wrong hands, so turning it off while it's in force takes a Face ID answer of its own (`POST /api/settings/passkey/options`, keyed `setting:faceIdForAgents:<credential>`; 403 without one), and the last passkey can't be removed while it's on (409: turn it off first). Turning it on is a plain tap. Recovery without the phone that has the passkey: passkeys sync across the owner's Apple devices, a new one can be added from any of the owner's devices, and at the Mac itself removing `passkeys.json` lifts it (the setting is in force only while a passkey exists).
- **Scope:** only the owner's admin devices, never invited or restricted access (guests, agents, Face ID-joined tagged devices are refused as before; a Face ID-joined browser can't approve at all while the switch is on). The Mac's own Touch ID, password and "allow" dialogs are macOS's and are not answered from the phone. The new routes are owner APIs: not in the public gateway's allowlist, and never answered to Funnel-marked requests.

Coverage: the switch (owner-account devices only, needs a passkey, persisted, off only with Face ID, the last passkey kept while on); approvals with the switch on and off; answers for another request, from another device, from another page, replayed, or made for a new browser's request or the switch; a credential with Deny; guests, a joined agent and a Face ID-joined browser on every route; a computer without a passkey or an https link; and in the browser, options before the tap, WebAuthn called in the tap for approving and for turning off, the answer sent with the decision or the switch, cancelled and refused answers retried with fresh options, another computer's page shown the Mac's refusal.

### Several computers, one phone (2026-10-04)

- **Linking** is a terminal action on each computer (`link <name>` in the running Reach), never an HTTP request. A computer lists only Reach computers signed in to the owner's Tailscale account (untagged, same user ID) whose public start page names the same host. Links are stored in the private data directory.
- **Approve once:** a device approved on one computer joins its linked computers without a terminal step, on a ticket: with its own credential it asks the computer it's signed in to for a one-use ticket (two minutes), and brings it to the linked computer. That computer redeems the ticket at the issuing computer's own address, over a TLS connection it opened and verified itself, and approves only the Tailscale user and node the ticket was issued to; the terminal names the computer that vouched. Both computers must have linked each other. A request with a ticket that doesn't check out is refused outright, so no request is left waiting.
- **Identity alone never approves:** any process running as you on a Mac can open Reach's private socket and claim one of your devices' Tailscale addresses (the socket takes the address it's handed). So a device's Tailscale identity alone approves nothing: not another browser on an approved phone, not a device approved on a linked computer without a ticket. Your approval, Face ID, or a ticket does (connections audit, Oct 10).
- **Revoke once:** revoking a device credential tells the linked computers. Each asks the sender back at its own address whether it really revoked that device before ending the credentials bound to that Tailscale node (sockets closed, screen control released). A process claiming a linked computer's identity can't make a computer revoke anything.
- **Same device:** browsers on a phone that uses the Tailscale app share its node, and browsers that signed in on their own (`iphone-browser`, `iphone-browser-1`) are separate Tailscale devices. Each new browser is approved once (or uses Face ID), then shows as one device in the access list and presence. That grouping is by name and affects display only, never access.
- **One page, all computers:** a linked computer accepts browser requests from the other computers' private and start-page origins (exact origins, updated when links change). The single link shown in every linked computer's terminal is the start page of the computer where Reach was set up first; each computer's own link keeps working.

### Invitations with detailed permissions and invite keys (2026-10-04)

- **Permissions** are enforced by each computer on every request, never only in the interface. Folders (read or read/write), screen (watch, or watch and control), apps (all or chosen, watch only), their own terminals, AI sessions, or full access. Full access can do anything the owner can, except manage access (devices, invitations, settings, agents, activity, linked computers). These routes are refused for every guest. App-only invitations see only the chosen apps' windows and installed-app entries; they can't open other apps' windows, stream displays, type into fields, quit apps or launch apps on the Mac's own screen. App control is not offered: keyboard input is posted system-wide and would reach whichever app is in front. Screen control needs the explicit "watch and control" choice, and the owner can always take the control lease back from a guest. New scopes (`screen:control`, `apps:open`) are never available to agents.
- **Folders by browsing:** the owner can share any folder, browsed from the shared locations (up to 20). Each one is resolved on the computer: it must be a real folder inside a shared location after following links, and never inside Reach's own private data (a folder that merely contains it is allowed, and the private files stay hidden). The guest's file access is rooted at exactly those folders: nothing beside or above them.
- **Apps:** guests watch app windows the owner opened on their phone. Only the owner, or a full-access guest, opens, resizes, closes or quits them, because opening an app can move its window off the owner's screen.
- **Binding:** a redeemed guest credential is bound to the Tailscale node that redeemed it, so a copied token doesn't work from another device.
- **Invite keys** (`./reach invites`): a Tailscale OAuth client with `auth_keys` and `devices:core` write and `policy_file:read`, limited to `tag:reach-guest`, stored owner-only (mode 0600) on that computer and never sent to a phone or browser. Before making invite keys (at most every ten minutes) Reach reads the tailnet policy again and makes no key unless guests reach only Reach's port; an unreadable policy counts as open. The setup checks it for real (token, device list, a short key created and deleted) before saving. Each invitation gets one single-use, preauthorized, non-ephemeral key for `tag:reach-guest`, valid for the invitation's duration. The key travels only in the link's fragment, and the start page removes it from the address bar at once. The guest's browser device is named after its invitation (`rg-<computer>-<invite>`). That computer removes it through the API when the invitation ends, is revoked, declined or left, or none of its clients still has access, and checks again 20 seconds after start and every 5 minutes, so a device isn't left behind while Reach was off. Devices are removed by the node ID they signed in with, so renaming doesn't keep one; a tagged guest device with no name of Reach's and no node Reach knows is removed after the join window. Untagged devices are never touched.
- **Tailnet policy is the owner's:** Reach prints the exact `tagOwners` entry and a grant limiting `tag:reach-guest` to Reach's port on the chosen computers. Tailscale rules only ever allow: if the policy contains a `"src": ["*"]` rule, guest devices can also reach whatever that rule allows, whatever Reach permits. `./reach invites` says so and suggests `autogroup:member`. Reach never edits the policy.

Coverage: linking and discovery filters; approve-once only with mutual links and a ticket issued to that device (made-up, reused or another device's tickets refused); ticket redemption for linked computers only; revoke-once across computers, forged revoke refused, including one claiming a linked computer's identity; CORS only for linked origins; the phone's automatic join (approved on a ticket, never a stray request), identity alone approving nothing, same-device grouping, one row per device; invitation scopes, default-deny for app-only, view-only and control guests, owner taking control back, full access without access management, terminal/AI guests seeing nothing of the owner's; invite-key setup, key shape, cleanup on expiry/revoke, untouched non-guest and foreign devices; the invite form's exact requests to each computer, all-or-nothing creation, the guest link format; guest acceptance on several computers, one refusing. Not yet run against a real Tailscale OAuth client or a physical iPhone.

### Changing access without a new link (2026-10-05)

- **What:** the owner changes what an invited person or agent may use from their row in People with access (`POST /api/guests/:id/access`). The invitation, its link, the credential, the device it is bound to and the time left all stay. Only your own devices can do this: the route needs `admin`, and `/api/guests` is refused for every guest.
- **Same checks as inviting:** one function builds a person's access for both inviting and changing (`guestAccess` in `server/core.mjs`), and one builds an agent's (`agentAccess`). Agents still get only agent scopes: never the screen, apps or managing access. `folders: "keep"` keeps the folders they have. When they have none, or had full access, folders are chosen again with the same resolution as inviting.
- **More access** works from their next request, since every request reads the credential.
- **Less access ends at once:**
  - Losing the screen or its control gives screen control back to you.
  - Their open screens, terminals and input connections are closed with "Access changed" and start over under the new access. Each of those also re-checks every second on its own.
  - A command they're running (an agent's `reach_run_command` job) is cancelled when they lose running commands, or when its folder is no longer theirs.
  - Their terminal processes and AI sessions keep running, just as when you end someone's access, and they can no longer reach them. You can end them from Terminals or Sessions.
- **Their phone follows:** guests' and agents' live connection now carries a fingerprint of their access, so their phone reloads what it may use within seconds of a change.
- **Several computers:** an invitation made for several computers carries one id on each (`group`), and the phone changes it on each in turn. Invitations made before this have no id, so they change on the computer shown.
- **Unchanged risk:** raising someone to Can work, Full access or Can run commands is now one tap. That is exactly what the open escalation from the bug bash makes unsafe, and the same descriptions show in the menu.

Coverage: view only to edit files with the same credential; back to view only refused on the next request; guests can't change access; validation shared with inviting (bad choices, folders to keep or choose, full access not keepable, your own devices and ended invitations refused); an unopened invitation opens with the new access; agents never gaining screen, apps or full access; an open terminal closed by the change itself (code 4002, before the per-second check); their live connection staying open and carrying the change, with more access cutting nothing; the group id across computers; the row menu's exact requests, the folder picker only where needed, both computers changed, a refusing computer named.

### First-run setup and one-token invite links (2026-10-05)

- **Guided setup** (`./reach` on a new computer, `./reach setup` later) only orchestrates existing checks: Tailscale sign-in, the owner account (with its one-line warning about what approved devices can do), invite links, background mode. Progress is a small file in Reach's private state; it holds no secrets. A computer configured before this flow, a background service, and runs without a terminal never see it.
- **Invite links from one access token.** The owner pastes a Tailscale API access token (in the terminal it is read without echo). Reach uses it in memory for four calls and never stores, logs or returns it:
  1. It reads the policy file as written (HuJSON).
  2. It inserts only its guest tag owner and one grant (guest devices reach Reach's port on the owner's computers). Comments, rules and formatting stay as they were.
  3. Tailscale validates the result, including the owner's ACL tests. In the terminal the owner sees and confirms the exact lines. The write uses `If-Match`, so a concurrent edit is never overwritten.
  4. Reach creates its own OAuth client: `auth_keys`, `devices:core` and `policy_file:read`, tag `tag:reach-guest` only. It saves only that client, as before. The client is deleted again if its own check fails.
- **Policy-write power is never kept.** No credential with `policy_file` access stays on the computer, so a stolen Reach folder can't rewrite the tailnet policy.
- **Reach never changes the owner's existing rules.** If the policy still lets everyone reach everything (`"src": ["*"]`), invited devices are covered by that rule too. Reach refuses the setup before any policy write or key creation. It explains the required narrowing, but does not apply it itself: narrowing that rule could cut off the owner's other tagged devices or people they shared devices with.

Coverage: setup order, saving, resume after a pause, one-section re-runs, the change menu, start over, the never-prompt cases. The policy patcher: default and older policies, comments and look-alike keys untouched, one-line and empty sections, idempotence, unreadable files refused. The token flow: success, nothing to add, a bad or expired token, Tailscale's own refusal, a concurrent edit, declining, cleanup of a failed client, the token never on disk. The phone route, including guests refused. The phone setup card, both ways. Run in a real terminal with Tailscale's answers canned. Not yet run against a real tailnet.

### Face ID for new browsers (2026-10-05)

- **What it replaces:** typing a new browser's request code at the computer. Nothing else changes. A browser that signs in to Tailscale itself (no app) is its own Tailscale device, and a web page can't identify the phone behind it. A passkey (Face ID or the device passcode, WebAuthn with user verification required) proves it's you instead.
- **Adding one:** only from a device this computer already approved (owner account, untagged, with a full-access device credential), never by guests or agents. The passkey is for this computer's own Tailscale name only. Reach keeps the public key, the credential ID, the counter, and when it was added and last used, in a 0600 file.
- **Using one:** it approves one pending request, made by that browser (its secret) on its own Tailscale device. The challenge is bound to that request and device, used once, valid for two minutes, with at most ten tries.
  - The response is accepted only if all of these hold: it comes from Reach's private link or start page on this name; its RP ID hash matches; user presence and verification are set; the signature is valid (ES256 or RS256); the user ID matches; and any non-zero counter goes up. Synced passkeys may report 0, which is accepted when the stored counter is also 0.
  - The credential is then issued by the existing approval path, so device grouping, linked-computer approval and revocation are unchanged.
- **What it doesn't do:** passkeys sync through your Apple or Google account, so one proves it's you, not which phone. This request-approval path requires your own Tailscale account. The separate public Face ID enrollment path above can admit a tagged browser using a verified passkey and one-use ticket. Remove a passkey in Settings → Access (say, after losing a phone); new browsers then need approval at the computer again.
- **Checking it:** the verifier has no dependencies (strict CBOR, COSE keys, authenticator data). It's tested against a software authenticator and against responses recorded from real authenticators (SimpleWebAuthn's test vectors, MIT), including Android registrations with extension data.

Coverage: every refusal (wrong page, wrong site, no Face ID, a bad signature, an unknown key, someone else's user ID, a replay, another request's or device's challenge, an expired challenge, a counter that doesn't go up, too many tries), RS256. End to end through a Reach checking Tailscale identity: added from an approved browser, a new browser approved and grouped as the same phone, a replay refused, another device, a guest, a tagged device and another account refused, removal. On the phone: Face ID called straight from the tap (Safari requires it), cancelled then retried, not offered for another computer's address or without Face ID, offered once after a browser sign-in, "Not now" remembered, the Settings list and removal. Not yet tried with real Face ID on an iPhone.

### Inviting an agent (2026-10-05)

- **What it gets:** the owner invites an agent from the phone (Share → Agent): a name, one computer, at least one folder, and read, edit, or edit and run commands, for 1 to 90 days. It never gets screen, apps, the owner's terminals or AI sessions, or anything that manages access, whatever is asked for; only someone signed in as the owner (not a guest, not an agent) can create one. Commands run as the owner's account: they start in the chosen folders but aren't confined to them. Jobs are limited to 30 minutes each. An agent policy file doesn't lock invited agents out: their folders and limits come from the invitation, still checked against what Reach shares.

Guest links with a key would have stalled and shown "already used or expired". The client now signs in with the key itself, as Tailscale's `tsnet` does, and only for a new node.

### Notifications (2026-10-06)

- **Who gets them:** only your own devices (paired owners, not guests or agents, including agent credentials with broad scopes) can subscribe (`/api/push` and `/api/notifications` require an owner device), and each notification goes only to devices still valid. Revoking a device deletes its subscriptions; a push service answering 404/410 drops that one.
- **Where requests go:** the computer only ever posts to the browsers' push services (Apple, Google, Mozilla, Microsoft hosts over HTTPS on 443, no user info), never to an address a phone chooses.
- **What they say:** iPhone Home Screen apps always show Reach's icon, so the text tells requests apart. Your own agents' chats show the chat's name, then the agent and the request itself: the start of its last reply when done, the command and folder name for a command approval (only commands that pass the hidden-character check), the question (never a secret one), or up to two file names. Mac prompts show macOS's own prompt text. Invited agents get Reach's fixed wording with their name and the action type, never their own reason, typed text, or handoff reason. Notifications never include verification codes. iOS hides the body on a locked phone unless previews are set to Always. Each message is encrypted for its phone (RFC 8291) and signed with this computer’s VAPID key (`push-vapid.json`, 0600). Titles, bodies, URLs, icons, and action identifiers are bounded or allowlisted.
- **The worker:** `/sw.js` opens the exact request, conversation, or handed-off app on Reach’s own origin. It never caches workspace or API responses. It caches fixed brand icons and short-lived, one-use notification action intents without credentials. Every push displays a notification. A browser-supported Deny button opens Reach and submits the saved intent using the paired owner’s authorization; a query parameter alone cannot authorize a decision.
- **Background delivery:** while owner subscriptions exist, Reach reads real pending requests on source changes, with a 30-second fallback. Resolved requests leave the bell. Hashed request identities and signatures avoid repeat notifications across polls and restarts without storing conversation text. Handoffs and access requests also notify directly from their events.
- **Setup and testing:** the main bell and chat headers expose setup instructions, permission status, and a test button. iPhone requires a Home Screen installation on iOS 16.4 or later and an explicit permission tap. `/api/push/test` targets only the requesting device's specified subscription and is limited to one test per fifteen seconds. Success means the push service accepted it, not proof the phone displayed it.
- **Controls after setup:** the bell panel offers per-browser switches for agent questions/approvals, computer prompts, app handoffs, and access requests. Preferences are saved with that browser’s private push subscription and applied before delivery. Pauses last one or eight hours and can be resumed early; suppressed requests remain in the bell but are not queued for a later burst. Explicit test notifications bypass category and pause filters. Turning off removes the subscription.
- **Limits:** notification rendering belongs to the phone. iPhone Home Screen apps retain Reach’s app icon and do not expose web notification action buttons; tapping opens the exact review. Supporting Android browsers can show provider icons and buttons, bounded by `Notification.maxActions`. Reach must run on an awake, online computer. Delivery and rendering on physical phones still need an on-device check.

Coverage (`test/push.test.mjs`, `test/notifications.test.mjs`, `test/notifications-ui.test.mjs`, `test/notify-settings-ui.test.mjs`, `test/public-start.test.mjs`): encryption vectors and decrypt, VAPID signatures, push-service allowlist, owner-only routes, revocation and expired subscription cleanup, background waits without an open browser, deduplication across failures and restarts, per-browser test delivery and failure reporting, notification click routing, the bell and Home Screen setup, permission denial and settings changes, and public worker serving without API exposure.



## Agent presets (2026-10-06)

- **One choice, four presets.** The owner invites a browser agent (Muse, ChatGPT agent, a Grok bot) with a name, a preset and a duration (15 minutes to 24 hours over the public Funnel link, joined within 15 minutes; the earlier form stays capped at an hour): **Full control** (the Mac as the owner uses it: screen, mouse, keyboard, files, a shell as the owner), **Apps** (only the chosen apps appear and take input), **Files** (chosen folders, read or read-and-edit, through the sandboxed helper) or **Read only** (screenshots, files, shared terminal output; no input). Scopes, the route allowlist, the tools and the native rules are derived from `policy.preset` on every request (`server/agent-presets.mjs`); a stored policy with legacy fields or a protected app grants nothing. The owner can lower a preset later; raising into Full control or Apps needs a new invitation from the phone, because those bind the approving phone through the host guard.
- **Protected UI targets and command guardrails** (`server/agent-guard.mjs`, applied by the server and `scripts/native/agent-desktop.swift`): known Reach/Tailscale windows, password managers, secure fields, security prompts, sensitive System Settings panes and developer tools are filtered or refused. Full control and Read only may hide additional apps. These checks use observed app identities, titles, addresses and focus; they are not an isolation boundary against malicious browser content or an agent with an unsandboxed shell. The shell's textual deny list cannot prevent equivalent commands, scripts or indirect paths from reading secrets or modifying Reach.
- **Host browsers are allowed.** Saved logins are the point of Full control and Apps; the 2026-10-06 review's "host browsers need isolation" rule is reversed for preset invitations. What that means is said in the invitation and the owner's form: anything running or signed in is open to the agent, pages can steer it, the deny list is not a sandbox, the shell runs as the owner.
- **The Mac's observed input target.** One native helper per session (`agent-desktop.swift`, fed rules as data) checks the window under the pointer or the focused element before an action. It refuses while the owner is using the Mac (HID idle under 1.5 s), and filters known protected and hidden windows from screenshots, including windows inside selected apps. The window system and global input are not transactional: focus, titles and content can change during capture or a multi-event action. Typed text receives the shell deny-list check only when a terminal or IDE was actually observed; switching from a browser to a terminal before native dispatch requires a retry. A helper's complete policy fingerprint is checked before dispatch and after sensitive results, so policy changes discard stale results.
- **One agent at a time, the owner first.** `server/agent-desktop.mjs` holds one lease per Mac: an action takes it for 2.5 s and each action extends it; another agent gets `409 busy` with the holder's name and when to retry. Screenshots are concurrent. The owner's phone control, Reach's pause and the owner's per-agent pause (the agent's sheet on Agents & people) refuse every action with `409 paused`. Stopping or lowering an agent kills its helper and releases the lease.
- **The shell** (`server/agent-shell.mjs`, Full control only): `/bin/zsh -c` as the owner, starting from a shared folder, with a clean environment, 60 s and 256 KiB limits, one command per agent and four overall. The starting folder and textual refusals do not confine filesystem or network access. Authorization is rechecked after logging, before dispatch and every 50 ms during execution; revocation kills the monitored process group and closes its audit record. Completed effects and deliberately detached processes cannot be recalled. Every attempt is logged (`action.type: "shell"`), including refusals and cancellations.
- **Files.** Files-with-editing goes through the sandboxed helper, which gained a `write` operation (whole file, ≤ 1 MiB, replaces an existing regular file or creates one, never through a link). Full control writes directly inside shared folders with the same no-link and size rules and the private-path check.
- **Visibility.** Agents & people lists every agent, what needs the owner first; an agent's sheet shows its preset, what it is using right now, whether it holds the Mac, its requests, Pause/Resume, its activity and Remove access (the same end as the old Stop: access ends and queued work is cancelled). Ended agents are under Ended. Each action records the app in the activity log.
- **Always access (2026-10-07).** Next to the durations, the owner may choose Always (`standing: true`, public link only, stored as `policy.standing`). It joins like any invitation: the link works once, within the 15-minute join window, with the owner's code approval. After that the access has no end time, only the owner's Remove access, and its session does not end after two silent minutes. The agent's browser is its identity: the page keeps the session in `localStorage` and the signing key stays non-extractable in IndexedDB, so the agent can close the tab and come back in the same browser with no new invitation. The used link is worth nothing to anyone else (a new browser gets "already used" and nothing reaches the owner). For a different browser, the owner reopens the link (`POST /api/browser/agents/reopen`, owner only): the browser in use is disconnected, and the same link works once more for 15 minutes, joining with the code approval like the first time. Only a fingerprint of the link is kept for this (`linkHash`, never sent to any client); it opens nothing unless reopened. This works for timed public-link presets too while they have time left. Trade-off, accepted by the owner: once an agent has joined with Always, port 443 stays on Funnel (the start page and the signed agent gateway, nothing else) until the owner removes its access. One-time invitations (15 minutes to 24 hours) are unchanged. Since 2026-10-09 a different browser no longer gets the access by opening the link: it shows a new code for the owner, and only the browser the owner approved reconnects at once.
- **Tools over the public link (2026-10-09).** Where invite links aren't set up, a Tools invitation is a public-link invitation (`transport: "funnel"`) and its command joins through Funnel instead of the tailnet (`scripts/agent-funnel.mjs`): no Tailscale key, nothing for the owner to set up. The agent's runtime makes its own P-256 key (owner-only `key.pem` in its folder) and signs every request, exactly as the agent page does, through the same gateway (`server/funnel-agent.mjs`): claim with the owner's code, a token bound to that key, each request checked against the preset's routes, replays and floods refused. Trade-off: unlike the tailnet route, the public link has no network wall in front of Reach, and a copy of the agent's folder (key included) works until the access ends; the tailnet route adds device isolation and credential rotation, so Always is offered for Tools only there.
- **One invite, the route chosen by the agent (2026-10-10).** A public-link Tools invitation names the Mac's private address too (the same name, Reach's own port, reachable only from the tailnet). The agent's runtime tries it first on every call and uses the public link only when it doesn't answer, trying the tailnet again a minute later; only a failure before the connection is made moves a request, so an action never runs twice. The signed gateway accepts the private host as well as the public one, for the same audience. An agent on the owner's tailnet (Muse with its own Tailscale, say) needs no public door.
- **Always on either route; a week unused ends it (2026-10-10).** Always is offered for Tools agents over the public link too. Public-link agents trade their credential hourly while they work (`POST /api/device/rotate` through the gateway, with their key; the new one takes over on first use, the old one works two more minutes, used after that both end and the owner is told). Any Always access, and any agent that trades, unused for a week since its last use ends for good; use is stamped at most every ten minutes. `agent.mjs keep` / `restore` carry an agent's access as one line for its vault; restored elsewhere it reconnects by itself, with the key the owner approved. The restore command fetches exactly the runtime the line was kept with, by its SHA-256 (`/agent-runtimes/<sha256>.mjs`; the computer keeps the newest 50 from the last 90 days), and checks it before it replaces anything.
- **The public door (2026-10-10).** Internet requests are answered only while a stranger must get in (a pairing, an invitation waiting, an agent whose page has to load: a browser agent, or a Tools agent before its first credential trade). Otherwise a request is answered only when its `Reach-Key` header names a key Reach knows (an agent's own, or one that ended within seven days, so it hears that it ended), and only for the signed gateway and the runtime download; anything else gets 404 before a byte is parsed. Known keys are re-read only when the credential store changed. Past 300 strangers' gateway requests in a minute, every stranger is refused for five minutes before any body is read or signature checked; the owner is told once; agents with access have their own lane and feel nothing. Floods reach Tailscale's relays before the Mac.
- **A person kept out by the host guard is told why (2026-10-10).** The guard is unchanged: while a Full-control or Apps agent is invited, waiting or connected, Reach answers only the phone that invited it (`server/browser-host-guard.mjs`), and it starts at the invitation on purpose, so opening the link later leaves no gap. A person refused by it, opening their invitation or with access already, now reads that someone else, an agent with full control, has the Mac and that they can come in once the owner ends or pauses it; their invitation is not spent (`unopenedInvitation` reads it without redeeming). The owner is told who couldn't come in, once per person every ten minutes. Everyone else the guard refuses reads the previous message.
- **Reach as an MCP server at a URL (2026-10-10).** Owner decision: hosted agents (claude.ai and Claude Desktop custom connectors, ChatGPT, Muse, Grok) connect to `https://<public name>/mcp` with OAuth (`server/hosted-mcp.mjs`): discovery, dynamic registration, an authorize page whose six-digit code the owner matches in Reach exactly as for any agent, PKCE (S256) required, tokens from `POST /oauth/token`. A hosted connection is a public-link agent record whose bearer tokens carry a connection id where a browser key would be (`browserBinding`), so admissions, the per-preset allowlist, credential rotation with copy detection (`settleRotation`) and the week-unused rule apply unchanged: the access token lasts an hour, the refresh token rotates on every refresh, and a refresh token used after its replacement took over ends the access and tells the owner. The trade-off accepted: a bearer token is a second way through the public door beside signed keys, because hosted clients cannot hold a key. Each hosted invitation has its own address, `/mcp/<id>` with its discovery and OAuth endpoints under it (the id is derived from the invitation; the record keeps its hash), so a stranger without the address can't claim a waiting invitation, and nothing at a shared address claims anything (owner requirement, 2026-10-10). The door (`listenPrivate`, `hostedMcp.admits`) answers those paths only for an address Reach gave out, checked by its hash before anything is read: registration and the authorize page while its invitation waits, the endpoint, discovery and token endpoint while its agent has access or ended within a week (so an ended agent gets 401 and asks again); a hosted invitation no longer opens the rest of the public link; strangers beyond 300 requests a minute are refused for five minutes, each source gets 60 a minute, and a tool call goes through Reach's inner routes as a request of Reach's own to its loopback port with the verified context as its identity (`hostedDispatch` in `server/index.mjs`), never through an owner API.
- **A Tools invite: the Mac's private address if the agent reaches it, else the public link (2026-10-10).** Owner rule: "keep it simple, use Tailscale." A Tools invitation is a public-link invitation that carries the Mac's private address (the `t=funnel` link). The agent's runtime tries the private address over Tailscale when its own machine is on the owner's tailnet, and uses the public link otherwise, every request signed by its own P-256 key, the same gateway either way (`join` and `scripts/agent-funnel.mjs`). The agent never joins the tailnet itself: the background join added earlier that day was removed. Command line invitations keep their one-time Tailscale key and join the tailnet as before. The Mac still accepts an older unopened Tools invitation made for the tailnet through the public link (`toolsLink` in `server/core.mjs`), as a public-link agent record with the owner's code, the preset's allowlist, hourly rotation and copy detection. An unopened Tools invitation keeps the window open (`funnelWindow`), as a person's does, for `agent.mjs` and the claim.
- **Agents follow the computer's runtime (2026-10-10).** An agent's join command still installs only the runtime its invitation names (audit M8). After that, its runtime compares itself with the hash the computer reports on `/api/device` and `/api/browser`; when they differ it fetches `GET /api/device/runtime` over its own authenticated route (agents only; the gateway allowlists it), whose hash is taken from the very bytes sent, and refuses anything whose SHA-256 isn't the one named. It loads the new tools from its own copy (`~/.reach-agent/runtime/`) while its MCP server keeps running (`notifications/tools/list_changed` when a list already went out), and replaces its `agent.mjs` for the next start (not when it serves several computers). Anything that doesn't check out keeps the current runtime. Only the bundle does this (esbuild defines `REACH_AGENT_BUNDLE`), never a source checkout. Trade-off: the computer an agent joined can now replace the program the agent's machine runs, where before that took someone running `curl` there; it is still only ever the bytes that computer serves. `REACH_AGENT_UPDATES=off` on the agent's machine turns it off. `dist/agent.mjs` rebuilds at start when any file esbuild bundled into it changed (`dist/.agent-inputs.json`, never served).
- **Reach updates itself (2026-10-10).** An npm-installed Reach checks npm's `dist-tags` for `@nalebc/reach` every six hours (nothing published reads as "no release", not an error) and offers a newer version once per version under Needs you and in Settings. Only the owner's own admin device sees or answers it (`/api/reach/*` is owner-device only, checked again in the handler). **Update** installs exactly the version shown, `npm install --global --prefix <the prefix npm installed this Reach in> @nalebc/reach@<version>`, never `latest` at install time and never with sudo; Reach recognizes only npm's own layouts and a folder it can write, and otherwise shows the command instead. After npm finishes, the installed version is checked before Reach restarts through the same path as a restart request. While the new files wait for that restart, agents aren't told about the new runtime (their tools would call routes the old server lacks). `reach update` asks in Terminal; run without one (an agent) it never installs. Agents report the hash of the runtime they run as `?runtime=` on `/api/device` and `/api/browser` (inside the signed path on the public link), so the owner sees which agents are current; an agent is called out for a one-time manual update only when it is known to run the command-line runtime (its own tailnet device, or one that trades credentials).
- **Always over Tools (2026-10-09).** Offered only where invite keys are set up, once the October 9 agent-access audit's conditions held. Only an agent on the tailnet device its own invite key made can claim it (`tag:reach-guest`; an agent already on the owner's tailnet is refused), with the owner's code approval. Its credential rotates hourly while it works and a copy used elsewhere ends the access; a week unused ends it too. Its device stays on the tailnet as long as the access lasts, decided by the Mac, and leaves by node ID however the access ends. Guests' isolation is checked before each key is made.

## Browser-agent security review — 2026-10-06

Scope: invited browser agents, their private/Funnel transports, supervisor approvals, selected-app exposure, file routes, terminal implementations and sandboxed scripts. The attacker may submit arbitrary requests with their own credential and execute an approved script inside the shared folder. A compromised kernel, malicious unsandboxed local owner process and historical full-trust CLI credentials are outside this boundary.

Confirmed findings and fixes:

| Severity | Finding | Enforced fix |
| --- | --- | --- |
| High | Owner download links bypassed the app-session owner-device guard. | Check the pinned device on `/download`, recheck credentials during streaming, terminate on revocation. |
| High | Revoking the supervising device left the agent's app access usable. | Require the exact live approver binding and include it in admission/credential verification. |
| High | Unreadable credential storage could appear to contain no guarded sessions. | Strict storage reads keep the host guard closed on corruption or deletion. |
| High | Parent-directory swaps could redirect unsandboxed file operations. | Descriptor traversal without symlinks plus a kernel sandbox for all browser file operations. |
| High | Broad shares allowed tampering with Reach code, runtimes and shell startup files. | Deny protected files/ancestors/runtime writes and reject home/system/install execution roots. |
| High | Existing signed-in browsers and arbitrary native input were not capability isolation. | Remove host input and host browser/webview sharing. Restoring control requires actual isolation. |
| Medium | Revocation/permission changes could leave native window targets or captures in flight. | Invalidate targets and abort pending captures on changes; reauthorize final results. |
| Medium | Rich document conversion ran native parsers on agent-selected files outside the file sandbox. | Disable that converter for agents; allow bounded authenticated downloads to their environment. |

Regression coverage includes malicious route aliases and forged capabilities; stale/pending/collected/restarted sessions; immutable invocation and session-only approval behavior; supervisor revocation; corrupted storage; symlink/hardlink attacks; active parent replacement; deterministic directory movement after opening; runtime/startup tampering; protected app grants; native compilation and view-only UI. Tests use temporary fixtures and mocked desktop I/O, not the owner's private screen. Passing tests do not certify absence of unknown vulnerabilities. Current app limitations and the remaining isolation work are documented in [Browser agent tools](BROWSER_AGENT_TOOLS.md).


Resource limits: protected file helpers are limited to four globally and two per session; approved scripts to two globally and one per session. File/image HTTP responses retain slots until completion/disconnect (eight globally, two per session), with a 30-second response deadline. These bounds do not impose a per-script disk or physical-memory quota. Production dependency audit (`npm audit --omit=dev`, with user approval) reported zero known vulnerabilities on 2026-10-06; development dependencies and the separate Go/Tailscale dependency graph are not covered by that npm result.


## Multiple browser agents — 2026-10-06

Owner-only session overview and stop APIs use invitation IDs rather than agent names. Stop-all requests carry an explicit snapshot, validate every ID before any revocation, exclude owner/guest/CLI credentials, and safely tolerate already-removed IDs. Stopping a browser session cancels its approvals, native app targets/captures and queued/running folder work without resetting another session.

Scripts and mutations use one per-Reach writer coordinator, with canonical root and device/inode ancestry checks, FIFO for overlapping roots, bounded waits, live authorization, and leases retained until native completion. Writer start and completion invalidate other agents' shared-folder mutation/script consent, including delayed creation of remembered approvals during log flushing. No sandbox or protected-app permission is broadened.

Regression coverage includes denied nonowner routes, no partial stop for invalid mixed IDs, newer invitations surviving snapshot stop, credential redaction, same-name session separation, per-session cancellation/history, parent/child and case-alias coordination, unrelated-folder concurrency, queue/time limits, revocation while waiting/running, and native script/mutation sequencing. Shared data, mutable script contents and external/owner writes remain explicit limits.

## Private browser-agent copies removed — 2026-10-06

The private working-copy feature (copy, review, apply and discard) has been removed. Copying large folders such as the Desktop could never work reliably. Browser agents invited with folders always use the real shared folders. **Note (2026-10-06):** with a preset invitation, Files with editing and Full control change files immediately, with no per-change approval (see [Agent presets](#agent-presets-2026-10-06)); invitations made with the earlier form keep direct reads, read-only commands and changes approved one at a time until they end. The owner-only reviewed write/check/delete operations were removed from the native file helper, and invitations that ask for `workspaceMode: "private"` are rejected. Clients created by the old feature no longer pass the agent policy.
- **One link per approved agent, either route (2026-10-08).** Owner decision: once an agent is approved, its single link keeps working until its access ends. Opening it from another browser (`redeemFunnelBrowser` → `rebind` in `server/core.mjs`) moves the access: the new browser's key becomes the binding, the old token and receipt are deleted in the same write, and an admission already marked approved is created so the page collects at once; nothing reaches Needs you. The owner gets a push and an activity entry, and the old browser's work is ended exactly as Reopen link ends it (`endSession`). Only agents the owner approved before (`approvedAt`), with a preset invitation (`linkHash`), unexpired and still permitted by policy, can move; a first claim still waiting, a denied one, an ended or revoked one never can. Moves are limited to six per minute per agent. Trade-off, accepted by the owner: after approval the link is a bearer credential for that agent's preset until the access ends; treat it like a password, and remove its access in Agents & people if it leaks. Approved preset sessions no longer end after silent minutes, and the public page stays answering for them until their access ends. The same link also works for an agent that is a device on the tailnet: its lookup goes to the computer directly, the signed gateway applies unchanged, and the gateway clears any Tailscale identity before inner routes run, so an agent under the owner's own login never acts as the owner. Every gateway refusal is marked `Reach-Not-Run: 1`; the agent page retries reads through drops and restarts for about a minute and repeats a write only when it carries that mark.
- **An agent with access never has to ask again (2026-10-08).** Owner rule: an agent is told to ask for a new invitation only when its access is over. The agent page treats a refused request as a reason to reconnect, not to forget: the gateway's `reconnect` operation (`reconnectFunnelBrowser`, `relink` in `server/core.mjs`) refreshes the session for the browser that holds it (new token, the previous one deleted in the same write; no notification, no `endSession`) and gives a browser whose claim answer was lost its same waiting request back (same code, new secret). Only opening the link (`claim`) moves access to another browser; an automatic `reconnect` from any other browser gets 423 and changes nothing, so two open browsers cannot take it back and forth. The page resends a request refused before it ran (`Reach-Not-Run`) once after reconnecting, adopts a session another tab already refreshed, and uses the stored token rather than a view's older one. Only these are final and clear the browser's credentials: 401 (unknown or revoked link), 403 (declined), 410 (expired or ended, or a request that expired before the owner approved it). The five-minute approval window is unchanged: a request the owner never answered still expires. The page no longer discards a session by its own clock; the computer decides, so an owner extension or a late approval is picked up.
- **Ended access is told it ended (2026-10-08).** While Reach runs and is not paused, the signed agent gateway (`POST /agent-gateway`, on the public route and the tailnet alike) answers even when no invitation or agent window is open; every other public request still gets "Not found." until one is. With no window open there is no unopened invitation, no waiting request and no granted agent, so nothing can be claimed, collected or used: the gateway only answers refusals, which lets a stopped agent's page read 401 and an expired one's 410 and stop, instead of retrying "Not found." forever. Paused or reconnecting is still 503. A reconnect never re-approves terms the owner did not approve: `rebindable` also requires the stored approval to match the current record (`admissionGrant`), so a change that fails closed, such as another supervising phone, stays closed. The owner's Reopen link (owner API only; no longer in the interface) now only disconnects the browser an approved agent is using; its link keeps working.
