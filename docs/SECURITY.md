# Reach security review — 2026-10-03

This is a source review and targeted regression test pass, not a penetration-test certification or a guarantee that no vulnerabilities remain. Scope: Node companion, pairing, scopes, file endpoints, PTY/WebSocket transport, Codex approval routing, launcher/distribution, browser request handling, and npm dependencies. Native iOS packaging received a limited source inspection; Windows and physical phones were not exercised.

## Verification

- Production TypeScript/Vite build and all 25 Node integration/security tests passed on macOS. CI also checks npm advisories at moderate severity and above.
- Real HTTP requests and PTY sessions against disposable folders, including mixed-case privilege-bypass attempts, exact hosts/origins, cross-client access, expired/revoked credentials, private-state paths, and pairing throttling.
- Live private Tailscale Serve smoke test on a separate port: pairing, file transfer, actual shell output, revocation, shutdown, and preservation of pre-existing Serve configuration. No public tunnel or Funnel enabled.
- Approved npm advisory lookup, then a clean re-audit after the dependency fix. [Underlying advisory](https://github.com/advisories/GHSA-w5hq-g745-h8pq).
- Local pattern scan of working source and available Git history for private keys, common provider tokens, Supabase secret keys, JWT literals, and AWS access keys: no matches. This is a limited pattern scan, not proof that every possible secret is absent.
- With the owner's explicit approval, restarted the older companion with its existing environment and port preserved. The live replacement rejects unauthenticated device access, unrelated browser origins/hostnames, and Funnel-marked requests.

## Remaining boundaries and limitations

1. **Reach controls the host OS account.** `exec`, `terminal`, screen control, and Codex are powerful capabilities. An agent with shell access can read local credential files or change the companion itself. API scopes/ownership do not sandbox that agent. Use a dedicated OS account, VM, or isolated computer for untrusted agents.
2. **File access is broad and includes writes.** Without `--folder`, the root is the home directory. A file credential can read sensitive files there and upload new files; hiding dotfiles in the interface is not a permission boundary. Use explicit shared folders. This pass does not claim to prevent symlink races caused by a concurrently malicious local process ; the new profile-based file API enforces per-agent roots as described below.
3. **Browser credentials remain in local storage.** An XSS vulnerability, malicious browser extension, or compromised trusted interface could steal them. Exact origins, CSP, expiry, and revocation reduce exposure; hardware-backed browser keys or an HttpOnly same-origin session design remain future work. No authenticated browser UI or physical-phone penetration test was performed.
4. **Tailnet access policy remains the owner's responsibility.** Serve limits network reachability; application pairing is an additional check. One-command setup requires an installed, signed-in Tailscale client and may require owner approval to enable HTTPS. Local processes can reach the loopback listener. The launcher does not automatically change tailnet grants or install a VPN.
5. **Revocation stops future API and socket access, not all existing effects.** Commands already started may continue; cancellation cannot undo filesystem changes or reliably contain deliberately detached subprocesses. Stop the relevant job/session or companion as appropriate.
6. **Not hardened for hostile public traffic.** There are limits on payloads, jobs, terminals, and pairing attempts, but uploads can consume disk space and authenticated workloads can consume host resources. Keep Reach private. Shared proxy-side rate limits can temporarily block other clients after repeated bad attempts.
7. **Distribution/runtime trust remains.** Node downloads are SHA-256 pinned and npm uses the lockfile; package lifecycle scripts still execute locally. Signed application releases, a sandboxed companion, and independent review remain outside this pass. Windows behavior and user-profile ACLs need device validation.
8. **Running processes must be restarted to receive fixes.** Editing source does not patch an already-running companion. Restarting ends its active jobs/terminals. The audit does not silently interrupt existing user sessions.

No Supabase administrative credential is needed for the default authentication flow. Each host holds its own pairing and client state; Tailscale handles private connectivity, and Reach verifies local client credentials.

## Screen feature follow-up

Screen viewing remains off by default. Input now requires a separate 30-second, memory-only control grant bound to one paired full-access client; a screen-scoped agent cannot acquire it. The browser renews while actively controlling and releases on pause, page hide, or unmount. Revocation and disabling viewing clear the grant. Native dispatch rechecks authorization after any helper compilation, and simultaneous input operations are rejected. Screenshot responses recheck viewing/auth after capture.

Validation includes control ownership, expiry, revocation, disabled-view behavior, payload bounds, and dispatch through an inert helper. The UI was exercised at phone width with a synthetic desktop fixture; the Swift helper typechecks. This does not establish real desktop capture/control or physical-device behavior. macOS permissions still require the user to grant access locally.

Continuous screen streams authenticate in the first WebSocket message and require the `screen` scope and enabled viewing. Exact Host/Origin and Funnel checks apply before upgrade. A shared native capture process runs only while viewers are connected, rechecks authorization before delivering frames, and stops on the last disconnect. Protocol-2 streaming limits viewers to four, frame bodies to 8 MiB, and each viewer to six unacknowledged packets; outgoing socket buffering is also bounded. Legacy streaming retains a separate four-viewer cap and one-frame window. Slow video viewers resume at a keyframe. Native helpers communicate only over local pipes; no additional network listeners or public signaling servers are introduced. Disablement closes all screen sockets; revocation closes the affected client’s sockets. Streaming does not grant remote input permission.

## Agent CLI follow-up

Named profiles bind short-lived agent credentials to API scopes and canonical folder roots. The server intersects the issued snapshot with the current local policy, so reductions apply to subsequent requests and expansions require a new grant. Missing/invalid profiles fail closed; configured policies reject legacy unprofiled keys. File mutations require `files:write`; file reads require `files:read`. Text edits require the last-read SHA-256 and atomically replace the file. These checks do not protect against a concurrently malicious local process swapping filesystem objects, and shell-capable scopes remain outside folder confinement. Existing command side effects are not undone by revocation.

The agent CLI stores credentials in exclusive mode-0600 files, refuses insecure secret inputs, validates TLS even through the loopback CONNECT proxy, and rejects redirects. The optional isolated Tailscale wrapper uses its own socket, ephemeral memory state, exact-tag verification, disabled incoming/SSH/routes, bounded lifetime and cleanup. It cannot establish that existing tailnet grants are narrow: owners must review additive ACL/grant rules. Same-user processes in the agent runtime are not isolated from its socket, proxy or mounted secrets. Workload identity trust, AWS IAM, tailnet changes and real cloud enrollment require environment-specific validation. See [Agent CLI](AGENT_CLI.md).

### Temporary guests

Connection settings lets an owner create a one-use guest invitation lasting 5 minutes to 24 hours (the API permits 1 minute to 24 hours). The fixed expiry starts at creation, includes time waiting for redemption, persists across restarts, and cannot be extended by the guest. A new invitation is required after expiry. Unused invitations can be revoked from the same client list.

Guests receive only selected shared folders with read or read/write access, and optionally view-only screen access. They cannot use terminals, execute commands, control the screen, manage clients, or issue new invitations. A 256-bit invitation secret is kept in the URL fragment, removed from browser history on opening, stored only as a hash on the laptop, and exchanged once for a different hashed credential under the credential-file lock. Guest browser credentials use session storage, separate from permanent owner pairing. Leaving revokes the guest credential.

Expiry is enforced by the laptop on every request, with deadline timers for active HTTP transfers and WebSockets. Early revocation closes WebSockets immediately and in-flight HTTP transfers within the one-second authorization check. Upload authorization is checked again before a completed upload is published. Downloads already received and completed file changes cannot be recalled. A guest may copy their credential before expiry; it still has the same scope and deadline, so the invitation is not an identity-verification mechanism.

These deadlines revoke Reach access. They do not remove a person or device from Tailscale or revoke access to other laptop services. Guests still need an independently authorized Tailscale path to this laptop. Configure the tailnet to allow only Reach's port when that is the intended boundary; Reach never applies tailnet-wide policy or logs the owner's laptop out of Tailscale.

### Encoded desktop and persistent input

H.264 video and input use separate authenticated WebSockets on the existing Reach listener. They do not open media ports or use external signaling services. TLS through Tailscale Serve and the private tailnet remain the deployment boundary; encoded video does not itself encrypt traffic.

The new persistent input channel requires the owner's explicit control grant and rechecks authorization before and after each native operation. Display IDs, coordinates, keys, modifiers, text lengths, message order, and rates are validated. A connection uses one native helper, serial native dispatch, a bounded eight-action pipeline, and bounded buffers. Authorization is rechecked immediately before queued actions are dispatched. Pointer moves are coalesced client-side. Native watchdogs release held mouse buttons after two seconds without traffic; normal disconnect closes the helper. These are best-effort cleanup under OS/process failure, not a guarantee against a forcibly killed or compromised host.

Clipboard transfer is text-only, explicit, and limited to 16 KiB. It uses the same owner-only control channel, is never automatically synchronized, and is not persisted by Reach. The preview remains in page memory until cleared or the screen view is unmounted. Guests and scoped agents cannot use input or clipboard even when permitted to watch displays. Screen permission covers the available displays; it is not a per-monitor privacy boundary.

Validation covers malformed input, guest isolation, expiry, revocation, drag ordering, shortcuts, clipboard authorization, bounded video delivery, keyframe recovery, and native Mac H.264 output from synthetic frames. Browser verification uses real encoded synthetic video and mocked input, avoiding capture or control of the user's desktop. Windows native helpers and physical iOS/Android gestures still need device testing. No claim of a gap-free security audit or benchmark parity with commercial remote-desktop products is made.

### Automatic desktop and app shortcuts

Performance changes preserve authorization checks at native dispatch and before sensitive responses. Pending input is cleared on close/revocation; native input remains serial even though network transmission is pipelined. Stale queued commands fail closed. Automatic video pacing and bitrate changes do not reconnect or widen permissions. App shortcuts require owner + apps scope and dispatch server-discovered installed app IDs, the fixed new-Codex-session action, or saved validated HTTP(S) website shortcuts. No user-supplied shell command, arbitrary URL scheme, or app argument is accepted. The shortcut's empty composer requires the user's next action before an agent starts work.

### Focused screen typing

Automatic field detection runs only after an owner-controlled click. It reads accessibility role, enabled/editable state, bounds, and password status, never the existing text or label. The helper returns an opaque in-memory focus token. Live edits and field keys verify that token and the current focused element immediately before dispatch. Focus can still change concurrently with OS input; this is a best-effort wrong-target guard, not transactional isolation. The browser keeps only the draft typed in this session, masks password drafts, and discards it when the bar closes or control ends. Existing owner-only control, expiry, payload bounds, and revocation checks apply unchanged. Native Windows behavior and physical-phone keyboards need device validation.

### Native phone editing and selection copy

The phone uses native text controls for selection, cut/copy/paste, autocorrect and dictation; their buffer is only text entered in the current typing session. Explicit manual keyboard entry can use legacy cursor-based input without a focus token when field detection is unavailable. Detected fields retain their focus guard. Copy selected text is an explicit owner-controlled action that reads only the current accessible selection, rejects password fields and limits UTF-8 output to 16 KiB. It does not invoke Copy and then race an old clipboard value. Existing control grants and post-dispatch authorization checks apply. Browser clipboard writes begin in the initiating tap; denied writes fall back to a selectable preview. No automatic clipboard synchronization or text logging was added.

### Saved custom shortcuts

Owner-only shortcut definitions persist as mode-0600 JSON inside the private data directory. App targets must resolve to the installed-app catalog, including at dispatch. Website targets accept only HTTP(S), reject credentials/control characters and are passed as a separate argument to the OS opener without a shell. They are explicit owner-requested navigation, not a server fetch or new network listener. No commands, arbitrary deep links or app arguments can be saved. CRUD and execution require both admin and apps scopes with authorization rechecks after asynchronous discovery. Validation covers persistence, edits, deletion, missing apps, input bounds and guest/agent rejection.

### Tailscale identity and local device approval

The configured Mac/Linux launcher uses a dedicated Unix HTTP/WebSocket listener, mode 0600 under a mode-0700 directory owned by the Reach OS user. On sandboxed macOS Tailscale variants this lives in the existing Tailscale app-group container; on CLI-only hosts it uses a private temporary directory. No Tailscale credentials/configuration files are modified. Only this listener can mark requests as trusted ingress. TCP localhost headers never establish identity. The OS user and root remain trusted: they already have access to Reach's credential files and the computer itself.

Serve overwrites forwarded source and identity headers. Reach resolves that source IP with `tailscale whois --json`; owner access requires the locally pinned numeric user ID and an untagged, non-expired node. Shared external users and tagged agents cannot become owners by presenting a pairing code. New browsers submit a bounded, five-minute request with a random claimant secret. A local terminal decision is required; there is no remote owner-approval endpoint. Claims require the same user/node and claimant secret. A 30-day Reach credential is bound to that identity on every HTTP and WebSocket authorization check, including screen-input checks. Missing Tailscale identity fails closed. Old unbound owner credentials require a fresh approval/pairing; scoped guests and agents retain their original permission model and require the trusted private ingress.

Pending requests and completed approval receipts survive a companion restart. A crash during credential issuance fails closed and asks for a fresh approval, rather than minting a duplicate credential. Retried claims return the same token rather than create another client; revocation cannot be undone by reclaiming the approval. The token is temporarily retained in a mode-0600 approval receipt for response retries, until the five-minute request expires; periodic cleanup runs every 30 seconds while Reach is running, and on subsequent requests. The main client store retains only the token hash. Browser sessions use local storage; pending request secrets use session storage. A copied token is unusable from another Tailscale node, but processes/browser scripts with access to the approved browser on the same node remain inside the trust boundary.

WhoIs lookups are coalesced and cached for two seconds, rather than run per input event/video frame. Active transfers/sockets refresh identity every two seconds, fail closed on lookup failure, and also expire stale identity locally. Reach credential revocation and screen leases retain their existing immediate/one-second enforcement. Tailnet removal is subject to Tailscale's own propagation and Reach's refresh interval, not an instantaneous global guarantee. Approval does not change tailnet ACLs, grant VPN membership, or enable Funnel.

Coverage: setup confirmation and malformed settings, unsupported Serve, TCP header spoofing, missing/invalid forwarded IP, wrong user/node, tagged owners, Funnel markers, pairing fallback gates, claimant-secret checks, expiry/denial/retry, copied credentials, scoped agents, authenticated WebSocket reconnect and revocation. Physical iPhone/iPad and Android onboarding remain hardware acceptance tasks.

Validation for this change: 136 tests passed, TypeScript/Vite production build passed, and the updated QR scanner passed Swift syntax parsing. A disposable Reach instance completed real Tailscale Serve identity lookup, a local approval, authenticated device access, and a retried claim on this Mac; its private route and temporary state were removed afterward. The browser preview verified pending-request reload, approval-to-workspace transition, and disconnected-phone guidance. This does not establish physical phone, Windows, or rebuilt native iOS app acceptance.

### Public start page and browser sign-in (2026-10-04)

This changes the earlier "no public tunnel" position, at the owner's request: phones without the Tailscale app must be able to reach a sign-in page. What is public, and what is not:

- **Public (Tailscale Funnel, port 443):** a separate HTTP listener on its own owner-only Unix socket (`server/public-start.mjs`). It answers only GET/HEAD for an allowlist: the start page (`/`, `/guest`), `/reach-start.json` (the private address, computer name and current Reach instance ID), hashed build assets under `/assets/`, the browser Tailscale client under `/tailnet/`, and the favicon, fonts and manifest. Anything else returns 404; WebSocket upgrades are dropped; other hosts get 421; misses are not cached, so arbitrary paths can't grow memory. Its CSP adds only `'wasm-unsafe-eval'` for the client. The app's code is public; it contains no secrets.
- **Private (unchanged):** Reach's API and WebSockets stay on private Serve (default 8443). Funnel on that port is still refused, and Funnel-marked requests are still rejected. Verified from outside the tailnet (public DNS): start files return 200, `/api/health` returns 404, and the private port refuses the connection.
- **App first:** the start page fetches `/api/health` on the private address. Only the start origin is added to the CORS allowlist for this check. If the answer comes from the same Reach instance, the phone already reaches the computer directly through the Tailscale app, and the page redirects there (keeping `#pair` / `#invite` fragments). Other origins still get 403.
- **Browser sign-in:** without the app, the page runs a Tailscale node compiled to WebAssembly (`tailnet/main.go`, based on Tailscale's `cmd/tsconnect`, pinned to `tailscale.com` v1.104.0). The user signs in on Tailscale's own login page. The node is a normal, lasting device on the tailnet, so tailnet policy, key expiry and device approval apply to it. Its key lives in the page's local storage for the start origin. Reach's API traffic travels inside WireGuard through Tailscale's relays (browsers can't send UDP, so there's no direct path), and TLS to the private address is verified inside the node. The computer identifies it with `tailscale whois` exactly like an app device, and owner access still requires approval on the computer. No logs are uploaded to Tailscale's log service.
- **Limits:** anyone who can script the browser profile can use its node key until it is removed from the tailnet. Safari may clear storage for sites that aren't used for seven days, which means signing in and approving again. Large downloads in this mode are assembled in memory rather than by the browser's download manager.

Coverage: public listener allowlist, methods, hosts, traversal attempts, upgrade refusal, Funnel-marked requests, manifest validation, stale-socket handling; Funnel route ownership (ours, free, taken), foreground restart with backoff, never replacing another service on 443, service-mode add and uninstall removal; browser transport (routing to the tailnet only, streaming Response bodies, abort, empty bodies, WebSocket events, close codes, send order, errors kept out of the Go runtime); start-page config validation, instance-checked probe, redirect targets and wrong-account detection. Live checks on this Mac: the browser path loaded the real app through a browser tailnet node, Reach identified the owner account (`/api/auth/method` eligible), and API round trips measured 17.6 ms median and 24 ms p90 through the Seattle relay. Physical iPhone acceptance is still pending.

### Several computers, one phone (2026-10-04)

- **Linking** is a terminal action on each computer (`link <name>` in the running Reach), never an HTTP request. A computer lists only Reach computers signed in to the owner's Tailscale account (untagged, same user ID) whose public start page names the same host. Links are stored in the private data directory.
- **Approve once:** when a device asks a computer for access, that computer asks its linked computers (computer-to-computer, identified by `tailscale whois` of the calling node, which must be a linked node of the owner's account) whether the same Tailscale user and node already hold an unexpired device credential. If one says yes, the request is approved without a terminal step, and the terminal names the computer that vouched. Both computers must have linked each other: a computer answers only linked callers, and believes only linked computers. The trust is transitive along chains of links: a device approved through B's vouching is then vouched for by B to its other linked computers.
- **Revoke once:** revoking a device credential tells the linked computers, which end the credentials bound to that Tailscale node at once (sockets closed, screen control released). Only linked computers may send this.
- **Same device:** a request from a Tailscale node that already holds an approved device credential is approved as the same device: browsers on a phone that uses the Tailscale app share its node. Browsers that signed in on their own (`iphone-browser`, `iphone-browser-1`) are separate Tailscale devices; they still need approval, then show as one device in the access list and presence. That grouping is by name and affects display only, never access.
- **One page, all computers:** a linked computer accepts browser requests from the other computers' private and start-page origins (exact origins, updated when links change). The single link shown in every linked computer's terminal is the start page of the computer where Reach was set up first; each computer's own link keeps working.

### Invitations with detailed permissions and invite keys (2026-10-04)

- **Permissions** are enforced by each computer on every request, never only in the interface. Folders (read or read/write), screen (watch, or watch and control), apps (all or chosen, watch only), their own terminals, AI sessions, or full access. Full access can do anything the owner can, except manage access (devices, invitations, settings, agents, activity, linked computers). These routes are refused for every guest. App-only invitations see only the chosen apps' windows and installed-app entries; they can't open other apps' windows, stream displays, type into fields, quit apps or launch apps on the Mac's own screen. App control is not offered: keyboard input is posted system-wide and would reach whichever app is in front. Screen control needs the explicit "watch and control" choice, and the owner can always take the control lease back from a guest. New scopes (`screen:control`, `apps:open`) are never available to agents.
- **Folders by browsing:** the owner can share any folder, browsed from the shared locations (up to 20). Each one is resolved on the computer: it must be a real folder inside a shared location after following links, and never inside Reach's own private data (a folder that merely contains it is allowed, and the private files stay hidden). The guest's file access is rooted at exactly those folders: nothing beside or above them.
- **Apps:** guests watch app windows the owner opened on their phone. Only the owner, or a full-access guest, opens, resizes, closes or quits them, because opening an app can move its window off the owner's screen.
- **Binding:** a redeemed guest credential is bound to the Tailscale node that redeemed it, so a copied token doesn't work from another device.
- **Invite keys** (`./reach invites`): a Tailscale OAuth client with `auth_keys` and `devices:core` write, limited to `tag:reach-guest`, stored owner-only (mode 0600) on that computer and never sent to a phone or browser. The setup checks it for real (token, device list, a short key created and deleted) before saving. Each invitation gets one single-use, preauthorized, non-ephemeral key for `tag:reach-guest`, valid for the invitation's duration. The key travels only in the link's fragment, and the start page removes it from the address bar at once. The guest's browser device is named after its invitation (`rg-<computer>-<invite>`). That computer removes it through the API when the invitation ends or is revoked, and checks again 20 seconds after start and every 5 minutes, so a device isn't left behind while Reach was off. It only ever removes tagged guest devices carrying its own prefix; a guest who renamed their device could keep it only until another live invitation of that computer ends.
- **Tailnet policy is the owner's:** Reach prints the exact `tagOwners` entry and a grant limiting `tag:reach-guest` to Reach's port on the chosen computers. Tailscale rules only ever allow: if the policy contains a `"src": ["*"]` rule, guest devices can also reach whatever that rule allows, whatever Reach permits. `./reach invites` says so and suggests `autogroup:member`. Reach never edits the policy.

Coverage: linking and discovery filters; approve-once only with mutual links; refusal for other owner devices and tagged nodes; revocation stops vouching; revoke-once across computers, forged revoke refused; CORS only for linked origins; the phone's automatic join (approved only, never a stray request), same-device approval and grouping, one row per device; invitation scopes, default-deny for app-only, view-only and control guests, owner taking control back, full access without access management, terminal/AI guests seeing nothing of the owner's; invite-key setup, key shape, cleanup on expiry/revoke, untouched non-guest and foreign devices; the invite form's exact requests to each computer, all-or-nothing creation, the guest link format; guest acceptance on several computers, one refusing. Not yet run against a real Tailscale OAuth client or a physical iPhone.

### First-run setup and one-token invite links (2026-10-05)

- **Guided setup** (`./reach` on a new computer, `./reach setup` later) only orchestrates existing checks: Tailscale sign-in, the owner account (with its one-line warning about what approved devices can do), invite links, background mode. Progress is a small file in Reach's private state; it holds no secrets. A computer configured before this flow, a background service, and runs without a terminal never see it.
- **Invite links from one access token.** The owner pastes a Tailscale API access token (in the terminal it is read without echo). Reach uses it in memory for four calls and never stores, logs or returns it:
  1. It reads the policy file as written (HuJSON).
  2. It inserts only its guest tag owner and one grant (guest devices reach Reach's port on the owner's computers). Comments, rules and formatting stay as they were.
  3. Tailscale validates the result, including the owner's ACL tests. In the terminal the owner sees and confirms the exact lines. The write uses `If-Match`, so a concurrent edit is never overwritten.
  4. Reach creates its own OAuth client: `auth_keys` and `devices:core`, tag `tag:reach-guest` only. It saves only that client, as before. The client is deleted again if its own check fails.
- **Policy-write power is never kept.** No credential with `policy_file` access stays on the computer, so a stolen Reach folder can't rewrite the tailnet policy.
- **Reach never changes the owner's existing rules.** If the policy still lets everyone reach everything (`"src": ["*"]`), invited devices are covered by that rule too. Reach says so in the terminal and on the phone, with the fix. It doesn't apply the fix itself: narrowing that rule could cut off the owner's other tagged devices or people they shared devices with.

Coverage: setup order, saving, resume after a pause, one-section re-runs, the change menu, start over, the never-prompt cases. The policy patcher: default and older policies, comments and look-alike keys untouched, one-line and empty sections, idempotence, unreadable files refused. The token flow: success, nothing to add, a bad or expired token, Tailscale's own refusal, a concurrent edit, declining, cleanup of a failed client, the token never on disk. The phone route, including guests refused. The phone setup card, both ways. Run in a real terminal with Tailscale's answers canned. Not yet run against a real tailnet.

### Inviting an agent (2026-10-05)

- **What it gets:** the owner invites an agent from the phone (Share → Agent): a name, one computer, at least one folder, and read, edit, or edit and run commands, for 1 to 90 days. It never gets screen, apps, the owner's terminals or AI sessions, or anything that manages access, whatever is asked for; only someone signed in as the owner (not a guest, not an agent) can create one. Commands run as the owner's account: they start in the chosen folders but aren't confined to them. Jobs are limited to 30 minutes each. An agent policy file doesn't lock invited agents out: their folders and limits come from the invitation, still checked against what Reach shares.
- **Joining:** the agent runs one command: it downloads `agent.mjs` (no secrets) from the computer's public start page and joins with the link. The link (`/agent#k=…&h=…&i=…`) works once and only within 15 minutes; its invite key lasts just as long. The browser start page never uses an `/agent` link (it only says it's for an agent), so a person opening it doesn't spend it. With the Tailscale app already on the agent's machine and on the tailnet, it connects directly. Otherwise it joins as its own `tag:reach-guest` node, running the browser tailnet client inside Node, without changing the machine's network. It joins as a lasting device named after its invitation and is removed when the invitation ends. Ending its access removes the device at once when the key came from the agent's own computer, which the dialog prefers. A key made by another linked computer leaves the device until the invitation's end, though without a credential it can do nothing.
- **On the agent's machine:** `~/.reach-agent` (0700) holds the credential and the node's state (0600 files, written before the invitation is used).
