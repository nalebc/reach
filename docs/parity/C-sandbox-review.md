# Windows sandbox: review of the first draft

Verdict: **fix-first**. Each issue must be resolved in the revision.

1. **blocker**: Reach's own code is missing from every Windows deny set, which allows a sandbox escape. On the Mac, jobs write-deny appRoot (server/browser-private-paths.mjs:39), and scripts and Files read-and-write-deny it (browserPrivatePaths:46). The design's denies (§4.1, §10) list dataDir, agentPolicyFile, .reach, ~/.reach-agent, Startup, PowerShell profiles, .ssh and browserPrivateNames, but never appRoot. A CLI agent with exec may be given Home (chooseFolders, core.mjs:610-635, allows a folder that contains dataDir), and on Windows the checkout normally sits in Home. Its job can then rewrite scripts/native/sandbox.cs or server/*.mjs. The next start rebuilds reach-sandbox-<sha12>.exe from the edited source (the source-hash cache) and runs it as the owner, with power to rewrite ACLs.
   - Fix: Put appRoot (code, node_modules, scripts/native/*.cs) in the deny set of all three sandboxed surfaces: write-deny for jobs, read-and-write-deny for scripts and Files, exactly as on the Mac. Add the Windows persistence points that match LaunchAgents and the rc files: the Startup folder, both PowerShell profile directories, Git Bash rc files and .ssh/authorized_keys. Add a test: a job with Home as its root that tries to write sandbox.cs and server/index.mjs must be denied, and the preflight AccessCheck must fail if appRoot is reachable.

2. **blocker**: The per-object ACE walk is undefined, or infeasible, for the roots Reach actually issues. On win32, config.roots is Home plus every drive letter (server/file-roots.mjs:12-20). Non-admin device jobs use it (index.mjs:3005 → resolve → client.agentRoots || config.roots). The Full preset adds path.parse(cwd).root, which is C:\ (agent-policy.mjs:121). chooseFolders lets CLI agents with exec share Home or a drive. Read-only and Full Files may share Home (validateBrowserRoot:82). §7.5 itself calls a drive-root ACE 'impractical and dangerous', and §3.1 still says grants come 'from config.roots (devices)'. A walk over Home also always meets reparse points: AppData compatibility junctions, WindowsApps AppExecLinks and OneDrive. Under §4.1 that aborts the whole grant, so the Home presets can never work. Mac jobs (agentShellSandbox) don't depend on roots at all.
   - Fix: Write a table: client kind × surface → exact grant set. Refuse, with a worded reason, any jobs or scripts grant whose root is a drive root, Home or an ancestor of Home. Never derive grants from config.roots. Run grant walks at invitation or admission time, with progress and a size bound, not inside the 10 s Files and 30 s script timeouts. State that read-only Files over Home uses the owner-token broker (see the Files-helper item), not ACEs.

3. **blocker**: The revocation and residue model is wrong. (1) An AppContainer SID is derived deterministically from its name (DeriveAppContainerSidFromAppContainerName), so DeleteAppContainerProfile doesn't make the SID 'resolve to nothing'. reach.sbx.<hash(clientId)> is stable for the client's whole life, so §4.2's mitigation and test #7 assert a property that doesn't exist. (2) agentRoots can change while a session is live (changeAccess; the check() watchdogs detect it), but the ledger only revokes on expiry or revoke. A root that is removed keeps its ACEs, and the same SID's next job can still use it. On the Mac the profile is rebuilt for every process. (3) The revoke walk uses the same OBJ_DONT_REPARSE abort-on-reparse rule. An agent can plant a junction in its root (sandboxed processes may create mount points to targets they can write), the walk aborts, and the ACEs survive. (4) Open handles keep their granted access after an ACE is removed. (5) Expiry fires no event; only auth.revoke (core.mjs:2092) does. (6) While a session is live, a file the owner moves out of the root keeps its ACE and stays reachable by full path. The Mac loses access at once (browser-file-boundary.test.mjs:85).
   - Fix: Preferred: one custom capability SID per root, created with DeriveCapabilitySidsFromName('reach.root.<hash(root)>'), ACE'd once on the root. Each launch receives only the capabilities for the client's current agentRoots, so revoking or changing roots needs no walk and takes effect on the next launch. Chrome's lpacChromeInstallFiles capability is the precedent. If the design keeps per-client package SIDs, it must diff ledger against current roots before every launch and finish the revoke first. Either way: the revoke walk must continue past reparse points, never abort. Kill the job before removing ACEs. Add a periodic sweep for expiry. Correct the §10 residue text and test #7 to the real property: no Reach-launched token carries that SID or capability any more.

4. **blocker**: The Files helper 'inside an LPAC AppContainer' can't be built as specified. The Swift helper opens the root and then calls sandbox_init on itself (browser-files.swift:215-216). Windows can't move a running process into an AppContainer. The design never says whether sandbox.exe re-launches itself as an LPAC child or impersonates a lowbox token. If it re-launches: the exe sits in config.dataDir (§2.1), which the same design DENYs to the package SID, so the LPAC child can't load its own image. Starting the .NET Framework 4.8 CLR under LPAC (registry, GAC, NGEN images, COM init) isn't in the probe matrix either, which covers only cmd, powershell and node. In both variants, handle-relative opens are still access-checked against the lowbox token, so read-only Files over Home needs the infeasible ACE walk over Home.
   - Fix: Use a broker model like Chromium's: the Files helper runs on the owner token (as §7.5 already does for Full control), with the NT handle discipline, final-path verification and the private-name and private-path check on the normalized name. Drop the AppContainer and ACE walk for Files, and write in the parity ledger that the kernel belt the Mac gets from sandbox_init is replaced by broker code. If lowbox confinement is kept, impersonate a lowbox token on the worker thread rather than relaunching. Put the helper exe in a directory outside dataDir with an explicit read+execute ACE. Add 'sandbox.exe under LPAC starts' to the probe.

5. **major**: Private-name denial can't be expressed with static ACLs, and the design applies it to the wrong surfaces. On the Mac, scripts and the Files helper deny any path with a private name component (.git, .npmrc, .config, .gitconfig, .ssh, …) through a regex (browser-scripts.mjs:107, browser-file-boundary.mjs:27), including names created during the run. On Windows a script with write access to the root can create .npmrc or .gitconfig, or a .git directory if none exists, and the new object inherits the root's ALLOW. If directories carry FILE_DELETE_CHILD, which is needed for delete and rename, the script can also delete or rename children whatever their own DENY ACE says. For example it can rename an existing .git aside and create a new .git/config with core.fsmonitor, which runs as the owner on the next git status (verify against the File Access Rights / FILE_DELETE_CHILD docs). Separately, §4.1 applies the browserPrivateNames DENYs to jobs as well. Mac jobs (agentShellSandbox) don't deny .git, .npmrc or .config inside roots, so git and npm would break in Windows jobs.
   - Fix: Use one deny set per surface that mirrors the Mac exactly: jobs = agentShellSandbox's read and write lists; scripts and Files = browserPrivatePaths plus private names. For scripts, have the helper scan the root after the run and before closing the job for new or renamed entries with private names, then fail and report (or quarantine) them. Don't grant FILE_DELETE_CHILD on directories that contain private names, and list the remaining gap in §10. Add escape tests: a script that creates .npmrc, renames .git aside, or creates .git/config.

6. **major**: The access masks are unspecified, and the obvious choices fail. 'GENERIC_READ|GENERIC_WRITE' ACEs written with SetKernelObjectSecurity aren't generic-mapped, so on the object itself they probably grant nothing; only inherited copies get mapped (verify). FILE_GENERIC_WRITE has no DELETE, so rm, rename, editors' atomic saves, npm install and git all fail; Mac jobs and scripts can unlink. There's no FILE_EXECUTE either, so programs and scripts inside the root can't run, while the Mac grants file-map-executable on the root (browser-scripts.mjs:100). The design also doesn't say whether directory ACEs are inheritable (OI|CI). Without that, files the job creates are unreadable once their first handle closes.
   - Fix: Specify exact masks: FILE_GENERIC_READ|FILE_GENERIC_EXECUTE for read, plus FILE_GENERIC_WRITE|DELETE for write (see the previous item for FILE_DELETE_CHILD). Directory ACEs get OI|CI; file ACEs aren't inheritable. Add unit tests on the produced SDDL, plus real-Windows tests for create→reopen, rename, delete and running a .js or .exe inside the root.

7. **major**: The design contradicts itself on jobs' child processes. §3.1 says Apple Events, open and osascript are 'covered by activeProcs=1 + CHILD_PROCESS_RESTRICTED' for jobs, while §6 gives jobs N=32. Mac jobs allow fork and exec. With CHILD_PROCESS_RESTRICTED or a limit of 1, `cmd /c git status` or `npm test` can't start any program. Under §6, nothing replaces the Mac's `deny process-exec /usr/bin/open,/usr/bin/osascript` and `deny appleevent-send`.
   - Fix: Jobs: no CHILD_PROCESS_RESTRICTED, and a process cap only as a fork-bomb guard (e.g. 256). Scripts: limit 1 plus CHILD_PROCESS_RESTRICTED. Spell out the Windows equivalents of open and osascript as probe-verified refusals (next item).

8. **major**: Brokered launches and UI isolation are missing. Nothing restricts USER and UI access: there are no JOB_OBJECT_UILIMIT_* limits (READCLIPBOARD, WRITECLIPBOARD, HANDLES, DESKTOP, GLOBALATOMS, SYSTEMPARAMETERS, EXITWINDOWS) and no separate desktop. Yet the Mac's deny-default blocks the pasteboard for scripts and Files, and vault secret fills go through the clipboard. The probe also never tests the real equivalents of `open`: ShellExecute of an https or custom protocol URL, DelegateExecute or COM protocol handlers whose AppID grants AppContainer launch permission, explorer.exe or `start`, the runas verb (an AppInfo or UAC prompt), and the Task Scheduler or WMI COM interfaces from a regular (non-LPAC) AppContainer. Any of these can start a process outside the Job Object and outside the sandbox.
   - Fix: Set JOBOBJECT_BASIC_UI_RESTRICTIONS (all of the above) for jobs, scripts and Files. Consider a private desktop (CreateDesktop) for jobs and scripts. Add each brokered launch to probe item 3 and to e2e test 3, with the assertion 'no new process outside the job' (snapshot processes before and after, and check parent and session).

9. **major**: The network claims are inconsistent and partly infeasible. Adding WFP or firewall filters, or changing loopback exemptions (NetworkIsolationSetAppContainerConfig, CheckNetIsolation), needs an administrator, but Reach runs unelevated. So the WFP 'belts' (§3.3, §5) and §3.1's 'Reach's port blocked by a WFP rule' can't be installed, and §5 then says no WFP is needed. §5 also says the Full-control shell is blocked from Reach's port and pipe, but it runs on the owner token with no AppContainer, so nothing blocks it (the Mac doesn't either; drop the claim). Loopback denial is checked only against 127.0.0.1, in CI. It should also cover ::1, the PC's LAN IP, its own tailnet 100.x IP and MagicDNS name (Tailscale Serve would hand the connection to Reach with the owner node's identity), and PCs where a third-party firewall replaces Windows Firewall. 'Reach's named pipe' doesn't exist on win32 today: agent asks are refused on win32 (agent-asks.mjs:325), and the private route needs the Unix socket (launch.mjs:99-100).
   - Fix: Remove the WFP and firewall belts, or mark them out of reach for an unelevated Reach. Before each jobs launch, run a runtime self-test in the same AppContainer: connecting to Reach's port on every local address must be refused, and a failure refuses the launch (fail closed). Extend the probe to every local address and the tailnet name. Require workstream D/H's pipes to use an explicit DACL with no ALL APPLICATION PACKAGES or ALL RESTRICTED APPLICATION PACKAGES.

10. **major**: Several Mac parity gaps are labelled 'gain' or 'byte-for-byte'. Jobs: the AppContainer (worse under LPAC, which §1 also applies to jobs) can't read %TEMP%, the npm cache, %APPDATA%\npm, nvm-windows, fnm or Volta Node installs, .gitconfig or Git Bash in the profile. Mac jobs read everything except secrets, so ordinary commands break. Scripts: the Node runtime gets no ACE. The Mac grants it explicitly (nodeRuntimeFiles), and user-scope Node under AppData would be unreadable. Limits: the 1 GiB job memory cap and the 32-process cap have no Mac counterpart, and PerJobUserTimeLimit adds up CPU time across all cores, so on parallel builds it trips well before the wall-clock timeout (timeoutMs goes up to 1 h). Full-control shell: KILL_ON_JOB_CLOSE and the caps kill `start app` and background survivors that the Mac's process-group kill leaves running, so it isn't 'byte-for-byte'. Its env list (SystemRoot, PATH, USERPROFILE, TEMP, COMSPEC) lacks APPDATA, LOCALAPPDATA, PATHEXT, ProgramFiles, USERNAME and others. reach_shell's description still says 'no … sandbox … macOS permissions still apply' (browser-tools.mjs:176).
   - Fix: Jobs: regular AppContainer, not LPAC. Point TEMP/TMP at GetAppContainerFolderPath. Record the profile-read loss as a parity break in the plan's table, or add read ACEs for named tool directories. Scripts: grant the runtime directory read and execute, or refuse when Node lives somewhere that can't be granted. Drop JOB_TIME, or set it to at least timeoutMs × logical CPUs. Full shell: no memory, process or CPU caps; kill the job only on abort or timeout, as the Mac kills only the process group. Build the env with CreateEnvironmentBlock(owner token, FALSE) plus REACH_AGENT=1. Make the tool wording platform-aware. List every remaining deviation in §10.

11. **major**: Hard links and reparse points refuse more than the Mac does, and the reparse handling breaks on ordinary PCs. Under §4.1, any nlink>1 file or reparse point refuses the whole grant. The Mac denies just those files and runs anyway, falling back to directory denial and refusing only above 2000 (browser-scripts.mjs:149-160). pnpm stores are full of hard links, and pnpm and npm workspaces use junctions. OneDrive Known Folder Move puts Desktop and Documents under cloud-file placeholders, which carry IO_REPARSE_TAG_CLOUD_* tags (non-name-surrogate; visibility depends on the placeholder compatibility mode, so verify). Dev Drive is ReFS, which §7.3 refuses outright. Separately, OBJ_DONT_REPARSE on a full DOS path is reported to fail every time, because \??\C: is itself an object-manager symbolic link. That would make §7.1's root open always return STATUS_REPARSE_POINT_ENCOUNTERED (Forshaw-reported, https://sec.today/pulses/e4b00503-3a32-4367-aed1-05269c00a541/; the Microsoft doc https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes says 'no reparse points will be followed'). Probe it.
   - Fix: Skip the ACE on hard-linked files and name-surrogate reparse points (IsReparseTagNameSurrogate, plus AppExecLink) and carry on; refuse only on scan errors or above a bound, as the Mac does. Treat cloud, WOF and dedup tags as data. Open the volume through its device path, or open the root without the flag, then open each component relative to its parent with FILE_OPEN_REPARSE_POINT and inspect the tag. For ReFS, compare the 128-bit FILE_ID_INFO on the helper side rather than libuv's st_ino. Add OneDrive Known Folder Move, a pnpm project and a Dev Drive to the real-PC acceptance list; CI has none of them.

12. **major**: The JS validation that §3.3 calls 'platform-neutral … the parity spec' isn't. parseBrowserScript accepts `\` and `:` inside quotes (browser-scripts.mjs:18). rejectOutsidePaths recognises only ~, / and ./ ../ forms (lines 44-46), so `type "C:\Users\me\.ssh\id_rsa"`, `"..\..\x"`, `C:/x` and `"\\host\share"` pass. rejectProtectedProgram misses tailscale.exe and reach.cmd. validateBrowserRoot's protected roots are POSIX-only (browser-private-paths.mjs:77), so C:\Windows, Program Files and ProgramData aren't refused. A rw Files or script root under a user-owned C:\ProgramData\<vendor> passes the WRITE_DAC check, and an agent could plant a DLL that a SYSTEM service loads. The Mac refuses /Library. within and isBrowserPrivatePath are case-sensitive startsWith checks. The §2.3 request example uses `sub\\a.txt`, which relative() rejects.
   - Fix: Add win32 branches. Recognise drive-letter, UNC, \\?\ and backslash paths. Strip .exe/.cmd/.bat before the protected-name check. Add protected roots: %WINDIR%, both Program Files directories, %ProgramData%, the Node runtime directory and %LOCALAPPDATA%\Programs. Compare case-insensitively. Add as-windows unit tests for each bypass string above.

13. **major**: The helper protocol has holes. Control frames go on the helper's stderr, but nothing stops the sandboxed child inheriting or writing that handle. If the child's stdout or stderr shares the control channel, it can forge {"t":"exit","code":0} or {"t":"result",…}. browser-file-boundary.mjs parses the JSON result from stdout and drains stderr (lines 77-78), so 'reused verbatim' is false. stdin carries the request and then serves as the end-of-input kill lifeline, but the existing code calls child.stdin.end(body) (line 87), which would tear the helper down at once. jobs.mjs drives its 1 s grace from the helper's 'exit' (lines 120-123). Under decision (b) the helper lives until drain or deadline, so `echo started & ping -t` stays 'running' and holds its slot. That breaks the jobs.test.mjs:25 contract the design says it ports.
   - Fix: The child gets only pipes the helper owns (PROC_THREAD_ATTRIBUTE_HANDLE_LIST, never a control handle). The helper relays child output in length-prefixed frames on one channel. The request is length-prefixed and stdin then stays open as the lifeline. In jobs.mjs's win32 branch, call end(code) from the main process's exit frame plus the 1 s grace, and keep the helper alive only to reap survivors at the deadline. Make the stub-helper unit tests assert that frames are rejected when they arrive on the data channel.

14. **major**: There's a lost-update race on DACLs. Grants are locked per root, but roots nest (Home and Home\proj, or two clients with overlapping roots), and other software also rewrites DACLs. Two walkers doing GetKernelObjectSecurity→SetKernelObjectSecurity on the same object can drop a DENY carve-out after the preflight AccessCheck has passed, which exposes a secret to a running job. The preflight also checks only the listed deny paths, not objects created inside them later. For example atomicJson rewrites clients.json as a new object, which takes its DACL from dataDir by inheritance.
   - Fix: Use one machine-wide ACL-mutation lock. Re-run AccessCheck under that lock right before CreateProcess. Make DENY ACEs explicit and OI|CI on each private directory, and check after each walk that the DENY is still first among the explicit ACEs. Add a test with two concurrent grants over nested roots.

15. **minor**: Smart App Control detection is right but incomplete. Microsoft's page confirms VerifiedAndReputablePolicyState 0=Off, 1=Enforce, 2=Evaluation (https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/appcontrol), and SAC can switch states by itself. A freshly compiled unsigned exe in %APPDATA% or dataDir is also blocked by AppLocker default rules, WDAC, Defender's ASR prevalence/age rule, and EDR heuristics, which see mass DACL rewriting in Documents as ransomware-like. Controlled Folder Access can block the unsigned helper's writes in Desktop and Documents.
   - Fix: Decide by a no-op launch self-test of the built exe at every start, not by the registry alone. Map each failure (SAC, CI, AppLocker, ASR, CFA access denied) to a worded refusal, keep the registry read only for wording, and never retry or fall back.

16. **minor**: The CI lane doesn't represent consumer PCs. GitHub-hosted Windows runners run as an elevated administrator and have no OneDrive, SAC, CFA or third-party firewall. Escape tests run under an admin token can pass for the wrong reasons: WRITE_DAC is always available and the groups differ.
   - Fix: Run the escape suite as a standard local user created for it, in a non-elevated session. Keep a real-PC checklist (OneDrive Known Folder Move, Dev Drive, SAC in Evaluation, CFA on) for phase 5.

17. **minor**: There are some factual and wiring errors. A low-IL restricted token can't VM_READ a medium-IL process (process objects carry NO_READ_UP), so that rejection reason is overstated; the conclusion still holds. Windows Sandbox needs Pro/Enterprise and hardware virtualization; nested virtualization only matters inside a VM. libuv sets st_dev from VolumeSerialNumber.LowPart and st_ino from IndexNumber or FileId, and on newer builds through a GetFileInformationByName fast path (https://raw.githubusercontent.com/libuv/libuv/v1.x/src/win/fs.c), not GetFileInformationByHandle, so the identity test must exercise both stat paths. PowerShell -Command isn't subject to execution policy, so the stated reason is wrong, although plan rule 3 still stands, and the plan's 'pwsh' for the Full shell contradicts the design's cmd. overrides.agentShellRun is a test-injection hook, and createAgentShell hands the Windows run a Mac env (PATH /opt/homebrew, SHELL /bin/zsh). It's unclear whether owner-device jobs keep today's powershell.exe path.
   - Fix: Correct the text. Wire the Windows shell runner through an explicit win32 branch at index.mjs:1072 rather than the test override, and ignore the env it's passed. Reconcile plan and design on cmd versus pwsh. State that own-device jobs on win32 keep their current behaviour unless changed deliberately, with a test.
